## 先分清三层字段名

同一个概念在三个层面有不同的名字。把这三层混在一起，是最常见的提交失败原因——尤其是照着 Python SDK 文档去填界面表单。

| 层                  | 谁在用                         | 命名风格        | 例子                                                     |
| :------------------ | :----------------------------- | :-------------- | :------------------------------------------------------- |
| SDK API 层          | 你在应用代码里写规则时         | snake_case      | `threshold`、`scope`、`control`、`stat_interval_ms`      |
| Console wire 层     | 你在控制台界面里填的字段       | camelCase       | `count`、`strategy`、`controlBehavior`、`statIntervalMs` |
| 配置中心 payload 层 | 最终写进 Nacos / Consul 的内容 | 按 profile 分叉 | 见下表                                                   |

你在界面上填的是**第二层**。但第二层不等于第三层——落到配置中心的实际 payload 会按绑定 profile 重新编码：

| profile            | 写进配置中心的字段名                                                                                                                            |
| :----------------- | :---------------------------------------------------------------------------------------------------------------------------------------------- |
| sentinel-python-v1 | 复用 wire 层：`resource`、`count`、`controlBehavior` 等                                                                                         |
| sentinel-java-v1   | 复用 wire 层：`resource`、`count`、`controlBehavior` 等                                                                                         |
| sentinel-rust-v1   | 复用 wire 层                                                                                                                                    |
| sentinel-go-v1     | 换成固定的一组字段：`resource`、`threshold`、`statIntervalInMs`、`tokenCalculateStrategy`、`controlBehavior`、`relationStrategy`、`refResource` |

> **提示** 所以「界面上填 `count`，写进配置中心也是 `count`」这句话**只对 Python、Java 与 Rust 成立**。Go profile 的配置中心里写的是 `threshold`。在配置中心里直接手改一条 Go 规则、照抄界面上的字段名，会写出一个运行时读不懂的对象。

> **提示** Go profile 的 payload 是**固定的一组字段**，不是按条件增删的：`statIntervalInMs` 恒为 1000，`tokenCalculateStrategy` 与 `relationStrategy` 恒为 0，`refResource` 恒为空字符串。这是 Go 编码器的输出约定，不是「条件字段写成空值」的通用写法。

> **提示** wire 层还有一层约束：受条件启用的可选字段在关闭对应条件时要整个省略，不能序列化成 null 或空字符串。

### 一个字段的三个名字

以流量控制的阈值为例，同一个意思在三层分别是：

| 层                 | 字段名      | 取值     |
| :----------------- | :---------- | :------- |
| SDK API 层         | `threshold` | 阈值数值 |
| Console wire 层    | `count`     | 阈值数值 |
| Go profile payload | `threshold` | 阈值数值 |

而「按哪个维度限流」这个概念：

| 层                 | 字段名                                         | 取值                       |
| :----------------- | :--------------------------------------------- | :------------------------- |
| SDK API 层         | `scope`                                        | 限流维度                   |
| Console wire 层    | `strategy`                                     | 0 直接 / 1 关联 / 2 调用链 |
| Go profile payload | `tokenCalculateStrategy` 与 `relationStrategy` | 恒为 0（直接匹配）         |

> **提示** Go profile 的载荷里同时出现 `tokenCalculateStrategy` 和 `relationStrategy` 两个都取 0 的字段，加上 `refResource` 的空字符串。它们是这个 profile 支持子集的直接体现：只支持直接匹配的 QPS 限流，因此关联与调用链两种策略没有对应取值。

## 流量控制字段

流量控制按资源限流，可以限 QPS 也可以限并发。阈值含义随阈值类型改变。

| 字段              | 单位与取值                                                     | 必填条件                     |
| :---------------- | :------------------------------------------------------------- | :--------------------------- |
| resource          | 非空字符串，最长 512 个字符                                    | 必填                         |
| limitApp          | default 表示不区分来源                                         | 必填                         |
| grade             | 1 表示 QPS；0 表示并发                                         | 必填                         |
| count             | QPS 时是时间窗内请求数；并发时是在途并发数。必须大于 0         | 必填                         |
| strategy          | 0 直接；1 关联；2 调用链                                       | 必填                         |
| controlBehavior   | 0 立即拒绝；1 预热；2 排队                                     | 必填                         |
| refResource       | 关联或调用链模式下的目标资源                                   | strategy 不为 0 时必填       |
| warmUpPeriodSec   | 预热周期，单位是秒                                             | controlBehavior 为预热时必填 |
| maxQueueingTimeMs | 最大排队等待，单位是毫秒                                       | controlBehavior 为排队时必填 |
| clusterMode       | 集群流控开关                                                   | 关闭时省略                   |
| clusterConfig     | 阈值类型、样本数、窗口毫秒数。窗口不得小于样本数且须整除样本数 | 集群模式开启时必填           |

> **提示** 同一条流量控制规则里，预热周期是秒、排队等待是毫秒。单位不一致是最容易填错的地方。

## 熔断降级字段

熔断保护的是下游依赖。判定条件有三种，阈值含义随之改变。

| 字段               | 单位与取值                                                                                 | 必填条件                 |
| :----------------- | :----------------------------------------------------------------------------------------- | :----------------------- |
| resource           | 非空字符串                                                                                 | 必填                     |
| grade              | 0 慢调用比例；1 异常比例；2 异常数                                                         | 必填                     |
| count              | 慢调用比例时是响应时间阈值（毫秒）；异常比例时是 0 到 1 的比例；异常数时是计数，必须为整数 | 必填                     |
| slowRatioThreshold | 慢调用比例阈值，范围大于 0 且不超过 1                                                      | 只有慢调用比例模式才需要 |
| timeWindow         | 熔断持续时长                                                                               | 必填                     |
| minRequestAmount   | 触发熔断所需的最小请求数，正整数                                                           | 必填                     |
| statIntervalMs     | 统计窗口，单位是毫秒                                                                       | 必填                     |

> **提示** 不能把比例当成毫秒或次数，也不能反向换算。慢调用比例和异常比例都是 0 到 1，不是 0 到 100。

## 热点参数字段

热点参数按参数值维度限流，需要运行时能可靠提取参数。

| 字段              | 单位与取值                                          | 必填条件 |
| :---------------- | :-------------------------------------------------- | :------- |
| resource          | 非空字符串                                          | 必填     |
| grade             | 当前页面只允许 QPS                                  | 必填     |
| count             | 阈值，正数                                          | 必填     |
| durationInSec     | 统计时长，单位是秒，正整数                          | 必填     |
| paramIdx          | 参数索引，从 0 开始                                 | 必填     |
| paramFlowItemList | 例外项：参数类型、具体值、阈值。单条规则最多 100 项 | 可省略   |

> **提示** 参数索引从 0 开始，不是 1。而且只在表单里填索引没有任何作用——参数必须真的进入运行时的埋点，运行时才会提取它。

## 系统保护字段

系统保护使用运行时整体的压力信号来保护入口。它没有资源名，因为保护的是整个进程。

| 字段              | 单位与取值                 | 说明        |
| :---------------- | :------------------------- | :---------- |
| highestSystemLoad | 整体负载阈值               | 可禁用为 -1 |
| avgRt             | 平均响应时间，单位是毫秒   | 可禁用为 -1 |
| maxThread         | 最大并发线程数，必须是整数 | 可禁用为 -1 |
| qps               | 入口 QPS                   | 可禁用为 -1 |
| highestCpuUsage   | CPU 使用率，范围 0 到 1    | 可禁用为 -1 |

> **提示** 五个阈值可以分别禁用，禁用的值是 -1，不是 0——0 是合法阈值。而且至少要启用一项。CPU 用 0 到 1，填 80 会被理解为 8000%。

## 来源访问控制字段

来源访问控制依据运行时解析出的调用来源决定放行还是拦截。

| 字段     | 单位与取值                                     | 必填条件 |
| :------- | :--------------------------------------------- | :------- |
| resource | 非空字符串                                     | 必填     |
| strategy | 0 白名单；1 黑名单                             | 必填     |
| limitApp | 英文逗号分隔的来源列表。每一项非空，去重后写入 | 必填     |

> **提示** 运行时必须能可靠解析来源。不要把客户端任意传入的字符串当作可信身份。

## 单位陷阱速查

下面这张表把文档里明确指出的填错点集中在一起。发布前对一遍。

| 字段                 | 正确单位或取值    | 常见填错        |
| :------------------- | :---------------- | :-------------- |
| highestCpuUsage      | 0 到 1 的比值     | 填 80 表示 80%  |
| 系统保护的未启用项   | -1                | 填 0            |
| slowRatioThreshold   | 大于 0 且不超过 1 | 填 50 表示 50%  |
| 异常比例模式的 count | 0 到 1            | 填 0.5 以外的值 |
| warmUpPeriodSec      | 秒                | 按毫秒填        |
| maxQueueingTimeMs    | 毫秒              | 按秒填          |
| statIntervalMs       | 毫秒              | 按秒填          |
| durationInSec        | 秒                | 按毫秒填        |
| paramIdx             | 从 0 开始         | 从 1 开始       |
| 熔断的 timeWindow    | 见下方说明        | 凭印象按秒填    |

> **提示** 熔断的 timeWindow 单位在规则文档里没有给出明确声明。已知的落地实现里 Nacos 编解码按毫秒处理，但文档未给出权威定义，填之前请以你实际部署的编码器实现为准，不要按 Java 惯例想当然。

## 条件字段什么时候该省略

受条件启用的可选字段，在关闭对应条件时要整个省略。不能序列化成 null、空字符串或 0——写进去等于声明这个条件是开着的。

wire 层不认识的字段名同样不会被静默删掉。校验记成 `unknown_field` 或 `unsupported_field`，整份候选被拒。宁可整份被拒，也不要让配置看起来生效而运行时按自己的理解解释。

省略和写 null 之所以不同，是因为运行时按字段是否存在来启用对应能力。字段存在就可能带来一份空规则集，字段不存在才是「这一条不适用」。

1. 打开规则工作台前先确认绑定上的 profile，按它支持的字段子集填。
2. 填完逐项检查条件字段：条件没开就把整个字段删掉，不留 null、空字符串或 0。
3. 单位逐个对一遍：秒和毫秒不要互相复制，比例确认落在 0 到 1，参数索引从 0 开始。
4. 保存后立刻跑校验，按 `issues` 里的 `path` 逐条改。校验给出 `validationId` 和 `candidateChecksum`，固化成版本后 `checksum` 必须和 `candidateChecksum` 一致。

| 字段                | 启用条件                          | 条件关闭时怎么写             |
| :------------------ | :-------------------------------- | :--------------------------- |
| `refResource`       | `strategy` 不为 0（关联或调用链） | `strategy` 为 0 时整个省略   |
| `warmUpPeriodSec`   | `controlBehavior` 为预热          | 不是预热时整个省略           |
| `maxQueueingTimeMs` | `controlBehavior` 为排队          | 不是排队时整个省略           |
| `clusterConfig`     | 集群模式开启                      | `clusterMode` 关闭时整个省略 |
| `paramFlowItemList` | 可省略                            | 不需要例外项时整个省略       |

> **提示** 「省略」和「填 0」不是一回事。系统保护的五个阈值可以单独禁用，禁用值是 -1，因为 0 是合法阈值；那是系统保护自己的规则，和条件可选字段不是一套机制。
