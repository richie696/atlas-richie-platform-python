## 来源和绑定是两件不同的事

来源登记回答「怎么连到这台配置中心」；规则绑定回答「这个应用的规则存在哪」。两者都要有，缺一个都无法读取规则。

规则绑定的四个组成：环境、应用、规则类型、配置位置，再加上运行时 profile 决定这个绑定允许什么字段。服务与控制台必须指向同一个配置位置——这是最常见的「规则读不到」原因。

浏览器只通过 Console API 登记来源、填写目标和读取状态，不直接连接 Nacos / Consul。Console 后端的 provider 适配器负责凭证解析、配置读写和独立回读；Runtime 从配置中心读取规则，向 Collector 上报运行事实。这是三条不同的链路。

| 配置中心 | 配置位置的字段               |
| :------- | :--------------------------- |
| Nacos    | namespace ID、group、Data ID |
| Consul   | datacenter、完整 KV key      |

## 三种认证方式

登记来源时可以选择认证方式。地址里不要携带密码或令牌。

| 方式           | 含义                                       | 适合谁                     |
| :------------- | :----------------------------------------- | :------------------------- |
| 无             | 目标不需要认证                             | 本机或内网测试环境         |
| 直接凭证       | 控制台直接持有并加密保存账号密码           | 单一控制台实例管理来源     |
| 部署侧凭证引用 | 控制台只保存一个引用，实际凭证由部署侧注入 | 多实例或需要轮换凭证的部署 |

> **提示** 凭证引用并不强制要求你部署密钥管理服务，它只要求凭证不由控制台自己保管。

## 登记一个来源

在系统管理的连接与采集标签里登记。登记只是记下怎么连，不会去改配置中心里的任何东西。

1. 进入系统管理，停在连接与采集标签。
2. 选择提供方类型 Nacos 或 Consul，填写服务地址。
3. 选择认证方式并填写相应信息。
4. 测试连接。连接失败时先看探测结果里的原因，再看网络白名单与证书。
5. 保存。保存后来源出现在来源列表，可供后续创建绑定时选择。

## 登记一个规则绑定

在规则页登记。绑定决定了控制台去哪里读、去哪里写，以及允许写入什么样的规则。

1. 进入规则页，找到规则绑定目录，点登记规则集绑定。
2. 选择部署环境与应用标识。目录为空时可以直接输入首次配置的标识。
3. 选择规则类型。绑定按类型区分，不同类型是独立的绑定。
4. 选择配置来源，并按上面的表填写配置位置。
5. 选择运行时 profile。只有 profile 支持的字段才能发布。
6. 保存后，规则目录里就出现了这个绑定的条目，可以读取配置中心。

> **提示** profile 决定能力上限。界面表单里有某个字段，不代表当前绑定能发布它——发布前的校验会拒绝，但更好的做法是填之前就按 profile 的子集填。

## 空数组、缺失与失败的区别

这三种情况在界面上长得不一样，但初学者常常混为一谈。分清楚它们，能省掉一半的排查时间。

| 读到的状态        | 含义                                 | 下一步                                     |
| :---------------- | :----------------------------------- | :----------------------------------------- |
| 空数组            | 这个位置确实存在，里面一条规则都没有 | 正常状态，可以开始写第一条规则             |
| 目标缺失          | 这个位置在配置中心里不存在           | 检查配置位置填错，或者还没在配置中心创建过 |
| 无权限 / 连接失败 | 读不到                               | 检查凭证与网络，不是「这里没有规则」       |
| 保留上次成功内容  | 本次读取失败，显示的是上一次读到的   | 先修连接，再重读；当前显示的内容不代表现状 |

> **提示** 发布是整体替换，不是增量补丁。这意味着「读到了 0 条」和「读不到」在后果上完全不同：前者可能是你刚清空了，后者可能是配置中心挂了。

## 来源连不上时按什么顺序查

连接失败的原因分属不同的层，按顺序排查比反复重试快。下面几步依次是地址、配置位置、凭证、网络白名单和信任根，最后是重测连接。

1. 先看地址格式。服务地址只能是 http 或 https，不能带用户信息、查询串和片段，主机名要么是合法 DNS 名，要么是规范写法的 IP 地址。密码和令牌不能放进地址，改由认证方式承载。
2. 再看配置位置。Consul 用 datacenter 加完整 KV key，Nacos 用 namespace ID、group 与 Data ID 三段。配置位置错了，连接测试仍然能过，但读取时找不到目标——这是「连得上却读不到规则」的主要来源。
3. 确认凭证。认证方式有三种：无、直接凭证、部署侧凭证引用。直接凭证由 Console 后端持有并加密保存，填错就是认证失败；凭证引用要求部署侧注入真实凭证，由后端在连接时解析使用，浏览器不会读回真实凭证，也不会拿它直连配置中心。
4. 确认网络白名单。来源目标白名单的格式是 提供方|主机名|网段,网段|端口,端口，多条用分号分隔。提供方名与主机名必须和实际目标一致，端口必须在允许列表内，网段必须覆盖部署侧出口地址。
5. 确认 TLS 信任根。私有 CA 签发的来源需要配置 PEM CA bundle，否则握手就失败。信任根配好并不等于可以跳过校验，证书校验与主机名校验仍然生效。
6. 最后重测连接。探测给出的失败原因是有限集合，不带任意异常文本：来源检查返回 connection、authentication、unsupported；系统管理的连接视图返回 network、authentication、unsupported、not-configured、no-probe。先确认看的是哪一组，再按原因分类排查。

| 检查项               | 怎么确认                                                                  | 不通过时                                                                             |
| :------------------- | :------------------------------------------------------------------------ | :----------------------------------------------------------------------------------- |
| 服务地址格式         | 只能是 http 或 https，不含用户信息、查询串和片段                          | 把密码或令牌从地址里删掉，改用认证方式承载凭证                                       |
| 配置位置             | Consul 用 datacenter 与完整 KV key，Nacos 用 namespace ID、group、Data ID | 连接测试能过但读取失败时，先回到这一项核对                                           |
| 凭证                 | 无、直接凭证、部署侧凭证引用三选一                                        | 直接凭证填错就是认证失败；凭证引用要查部署侧的注入                                   |
| 来源目标白名单       | 提供方\|主机名\|网段,网段\|端口,端口，多条用分号分隔                      | 提供方名、主机名、端口任一不匹配都会被拒绝                                           |
| TLS 信任根           | 私有 CA 需要配置 PEM CA bundle                                            | 缺信任根时握手失败，补上后仍保持证书与主机名校验                                     |
| 测试结果里的失败原因 | 来源检查返回 connection、authentication 或 unsupported                    | connection 查网络与白名单，authentication 查凭证与信任链，unsupported 查提供方与参数 |
