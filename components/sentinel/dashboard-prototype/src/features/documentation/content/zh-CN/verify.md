title: 怎么确认接入成功：三层验证
summary: 读到了、加载了、真拦住了——三件事要分开验。
prerequisite: 已经登记了来源与规则绑定，并且有一个能发起请求的测试服务。
outcome: 对每一次接入都能给出三层独立的证据，而不是只看到「规则页有规则」。
---

## 为什么必须分三层

配置中心里能看到规则，只能说明那段文字存在。它既不能说明进程加载了它，也不能说明请求被挡住了。这三层各有各的失败原因，也各有各的观测点。

| 层       | 验证什么                     | 观测点                     | 常见失败原因                           |
| :------- | :--------------------------- | :------------------------- | :------------------------------------- |
| 一、读到 | 配置中心里的内容能被正确解析 | 规则目录的读取状态与规则数 | 配置位置填错、凭证不对、profile 不匹配 |
| 二、加载 | 某个进程接受了这份快照       | 实例加载状态、成员指纹     | profile 不支持、身份未登记、进程刚重启 |
| 三、执行 | 限流器在运行时真的起作用     | 业务请求的拒绝响应、指标   | 资源名对不上、阈值单位错、窗口不对     |

## 第一层：读到规则

先在控制台侧读。规则目录点读取配置中心，看规则数和读取状态。

1. 在规则页选中对应绑定，点读取配置中心。
2. 确认状态是「当前快照」而不是「过期快照」或「尚未读取」。
3. 确认规则数不为零。若为零，确认这个位置确实存在且规则数组为空，而不是读取失败。
4. 在业务进程侧确认同一份内容被正确解析。Java 和 Go 的 demo 都可以通过 /rules 查看。

```bash

curl -s http://127.0.0.1:18081/rules
```

> **提示** Java 与 Go 的 /rules 输出是纯文本键值行（rules_loaded、rule_count 等），Rust demo 返回 JSON。读不到 rules_loaded=true，说明进程还没拿到有效快照。

## 第二层：实例加载

这一层看的是运行时上报的加载观察，不是配置中心的内容。规则页的实例使用情况就是从这里来的。

1. 确认该应用有已登记的 Reporter enrollment。预期实例数未知时，界面显示未知而不是零。
2. 在规则页展开实例使用情况，看是否有实例确认加载。
3. 如果显示未知，去看成员清单是否完整、profile 是否匹配、观察是否过期。
4. 进程重启后旧的加载回执不再适用，需要等新的观察。

> **提示** 成员清单不完整、未协商或观察缺失时，界面必须显示未知。把未知当成「没加载」会得出完全相反的结论。

## 第三层：真的拦住了

只有业务请求的实际响应能证明第三层。用一个明显低于生产容量的阈值，效果最容易观察。

1. 先在无请求状态下确认 /rules 已加载。
2. 连续发起超过阈值的稳定流量，观察拒绝响应。
3. 记录响应序列。真实 provider 验收记录里，阈值 3 时连续五次请求得到 200, 200, 200, 429, 429。
4. 回到控制台，确认总览出现被拦截的计数，实时监控出现请求拦截率曲线。

```bash

for i in $(seq 1 5); do curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18081/api/hello; done
```

> **提示** 3 QPS 是为了容易观察而选的测试值，不是生产推荐值。另外多条规则可能同时匹配同一个请求，拒绝原因要结合具体资源和实际生效的快照判断。

## 改了规则多久生效

规则内容是轮询拉取的，不是推送。三个 demo 的轮询周期都是一秒。

| 环节             | 典型延迟       | 谁负责             |
| :--------------- | :------------- | :----------------- |
| 配置中心内容变更 | 立即           | 配置中心           |
| 进程拉到新内容   | 最多约 1 秒    | 运行时轮询         |
| 加载观察上报     | 再一个上报周期 | Reporter           |
| 控制台显示已加载 | 再一个采集周期 | Collector 与控制台 |

> **提示** 看到「规则页还是旧内容」时，先等一轮再判断。急着改配置中心的内容可能让你把内容改乱。

## 四种常见误判

三层验证的目的是把「读到」「加载」「执行」拆开。下面这四种误判都出现在这三层之间，共同点是拿一层的证据去回答另一层的问题。

| 误判                                       | 为什么是错的                                                                     | 该拿什么证据                                                                                                                                         |
| :----------------------------------------- | :------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------- |
| 配置中心读到规则了，就认为规则已经生效     | 读到只证明那段内容能被解析，不能证明任何进程接受了它                             | 看实例的加载观察：成员清单完整、该规则的成员指纹匹配、观察是新鲜的                                                                                   |
| 加载观察里有值，就认为当前生效的就是这一份 | 加载观察里有四个各自独立的值：来源修订号、来源字节摘要、规范化快照摘要、成员摘要 | 逐个比对来源修订号与成员指纹；其中一个变了不能推断另一个也变了                                                                                       |
| 有一次请求被拦住了，就认为所有实例都拦得住 | 拦截发生在单个进程里；实例清单不完整时界面显示未知，不代表其它实例也已生效       | 在实例使用情况里逐个确认，或对每个实例分别发起一组超过阈值的请求                                                                                     |
| 发布接口返回 202，就认为规则已经写完并生效 | 202 只表示服务端接受了这一个幂等操作，不表示 provider 已写入或实例已加载         | 看发布回执状态（applied / pending / failed / unknown / restart_required），再等实例加载观察确认；failed 不等于 provider 写失败，unknown 也不能算成功 |

> **提示** 这四种误判的共同后果是「提前宣布成功」。提前宣布成功的代价远高于晚一点宣布成功：晚一点最多是多等一轮轮询，提前则会让一次根本没生效的变更被当成已上线的保护。
