## 3 つの異なるゼロ

「使用インスタンス 0」にはまったく異なる意味があり、対処も異なります。

| 表示                                  | 本当の意味                                                       | 対処                                                                |
| :------------------------------------ | :--------------------------------------------------------------- | :------------------------------------------------------------------ |
| インスタンス 0 件（登録済み一覧が空） | 公式の一覧で現在登録済みインスタンスが無いことを確認済み         | まず Reporter を接続し、enrollment を完了します                     |
| 不明                                  | 一覧または観測のカバレッジが不完全                               | 観測がそろうまで待つか、enrollment が取り消されていないか確認します |
| 読み込み 0 件                         | 一覧は完全だが、このスナップショットにこのルールが含まれていない | 現在のスナップショットにルールが含まれるか確認します                |
| 期限切れ                              | 観測は存在するが古い                                             | プロセスが再起動していないか確認し、報告し直します                  |

> **注記** 「未観測」と「確認済みで存在しない」は別物です。対象一覧が不明なときは不明と表示し、確定したゼロを表示してはいけません。

## メンバー指紋が完全で、一致して初めて読み込みの証明になる

読込観測にはメンバー一覧があります。どのルールが実際にこのスナップショットに含まれているかを表すものです。一覧が完全で、かつ質問対象のルールと一致して初めて、そのルールが読み込まれたと証明できます。

観測には実は 4 つの独立した値があり、互いに代用できません。ソースのリビジョン番号、ソースのバイトダイジェスト、正規化スナップショットのダイジェスト、メンバーのダイジェストです。どれか 1 つが変わっても、別のものが変わったとは推断できません。

1. まずメンバー一覧が完全か確認します。
2. 次に、そのルールのメンバー指紋が一致するか確認します。
3. 最後に、この観測の鮮度を確認します。
4. 3 つとも満たして初めて、「このインスタンスは当該ルールを含むスナップショットを読み込んだ」と言えます。

## この順序で切り分ける

ルールが確かに存在しているのに、インスタンスが未読み込みと表示されるときは、次の順で確認します。

1. ソースの位置を突き合わせます。コンソールのバインディングの位置と、業務プロセスが実際に読んでいる位置が同じか。
2. バインディングの profile と、プロセスが実際に交渉した profile が同じか確認します。
3. 証明書の識別を突き合わせます。Reporter は enrollment 済みか、プロセスの起動識別子が現在と一致しているか。
4. 直近の Collector 受信時刻を確認し、報告経路がつながっているか判断します。
5. 管理型公開であれば、バインディング識別子、公開識別子、対象版識別子の 3 つを突き合わせます。
6. ネイティブルールなら、読込観測を確認します。ネイティブルールは公開識別子を生成しません。存在しない公開記録を探さないでください。

> **注記** ネイティブルールは読込観測を使います。公開 ID を偽造することはありません。ネイティブルールのページで公開 ID を探しても見つからないのはバグではありません。

## 期限切れと不明は別物です

期限切れは、この観測は古いものの、かつて有効だったことを示します。不明は、この情報がそもそも完全には確立されていないことを示します。

期限切れの観測は期限切れとして表示され、ルールが読み込まれていないとは推断できません。プロセスの報告が一時的に止まっている可能性があるからです。本当に行うべきは、報告が止まった原因を確かめることです。

## インスタンス識別子とプロセス周期

「使用インスタンスが 0 / unknown」を判断しにくいのは、インスタンス識別子の下にプロセス周期という層が隠れているためです。enrollment で登録される識別は 4 段構成です。環境、アプリケーション、インスタンス、プロセス。前の 2 段がデータがどのアプリケーションに属するかを決め、3 段目がどのインスタンスかを、4 段目がどのプロセスかを決めます。

プロセスの再起動は新しいプロセス周期識別子を生成します。同じインスタンス識別子が新しい周期で初めて報告するまでは、前の周期の読込観測が残ります。ただしその観測に答えるのは前のプロセスの問題です。

1. まず enrollment に登録された 4 段の識別がそろっているか確認します。環境、アプリケーション、インスタンス、プロセス。どれか 1 段でも欠けていれば、このプロセスのデータは目的のインスタンスに割り当てられません。
2. プロセス再起動後、インスタンス一覧で周期識別子が変わった項目を探します。前の周期は消えませんが、歴史にまとめられ、それぞれの状態で表示されます。superseded は新しい周期に置き換えられたこと、revoked は登録が取り消されたこと、no_current_epoch は現在有効な周期がないことを示します。
3. 前の周期のイベントは個別に表示され、現在のルールの使用状況には含まれません。前の周期の観測で「いま有効な版はどれか」に答えると、期限切れの結論になります。
4. プロセスが交代したら、まず一覧を更新してから、現在のプロセスを明示的に選択します。以前の読み込みの受信確認と公開の受信確認は新しい周期には適用されないため、もう一度確認が必要です。
5. ホストの関連付けもプロセス識別を持ちます。環境、ホスト、アプリケーション、インスタンス、プロセス、そして関連付け自身のリビジョン番号です。プロセスが交代したら関連付けも再確認し、前回のセッションでの関連付けの結論を引き継がないでください。

> **注記** 画面はプロセスの交代を検知すると明示的に注意を表示します。「一覧を更新して現在のプロセスを明示的に選択する。古い読み込みの受信確認は適用されない」という内容で、この注意は上の手順と同じことを示します。表示されたら従ってください。古い項目を読み続けないでください。
