## 毎日何を確認し、どの順に見るか

点検のポイントは、同じ時間窓と同じ絞り込み条件を維持することです。窓を変えて比較すると、違いを自分で作ってしまいます。

1. 概要で環境、アプリケーション、時間範囲を選び、まず全体のリクエスト量、遅延、ブロック、リソース負荷を確認します。
2. 要確認のアプリケーション一覧を確認し、異常なアプリケーションを洗い出します。
3. アプリケーションとインスタンスに進み、単独のインスタンスか、一部か、アプリケーション全体かを判断します。
4. リアルタイム監視に進み、同じ環境、アプリケーション、時間範囲を保ったまま曲線の前後関係を比較します。
5. 最後に障害分析で、この期間に対応するイベントの有無を確認します。
6. 使用した時間範囲、対象にしたアプリケーションとインスタンス識別子を記録します。後から振り返りやすくするためです。

## 誤読しやすい関係

次の組み合わせは、グラフ上では因果のように見えても、実際には相関にすぎません。

| 同時に現れた変化                            | 可能性                                     | 断定できないこと                                   |
| :------------------------------------------ | :----------------------------------------- | :------------------------------------------------- |
| HTTP QPS が下がり、リクエスト拒否率が上がる | 流量制限が働き、リクエストがブロックされた | 流量制限の閾値が適切だとは断定できません           |
| RT が上がり、CPU は正常                     | 下流、データベース、ネットワークの待ち     | アプリケーション自身に問題がないとは断定できません |
| トラフィックが落ち着き、イベントが消えた    | イベント報告経路が切断された               | 問題が復旧したとは断定できません                   |
| CPU が上がり、RT も上がる                   | 演算能力がボトルネックになった             | トラフィックが増えたためとは断定できません         |

> **注記** 相関は因果ではありません。結論を出すには、公開記録、読込観測、イベントの証拠に戻って確認する必要があります。

## 障害分析の使い方

障害分析は、負荷、応答の遅延、ブロックの増加、ルール公開を 1 本の証拠タイムラインにまとめます。

1. 環境、アプリケーション、インスタンス、時間範囲で絞り込みます。
2. さらに重大度と種別で絞り込みます。重大なイベントは対応が必要で、警告のイベントは継続観察します。
3. 新しい順のタイムラインからイベントを明示的に選び、観測された事実を確認します。
4. イベントの発生前後に、公開、バージョン切り替え、ソース読み取り失敗がないか照合します。
5. その期間に実際に読み込まれたスナップショットの版を照会します。
6. 推奨される操作に従います。関連するアプリケーション、インスタンス、ルール版を開きます。

## イベントが空でも健全とは限りません

障害イベントは独立したランタイムのイベント経路から届きます。イベントがないのは、実際に問題がないからかもしれませんし、イベントソースがそもそも接続されていないからかもしれません。

イベント一覧の集計基準は、現在の絞り込みウィンドウ全体の件数です。種別、レベル、ページングには影響されません。「すべてのイベント 0」と表示されて初めて、本当にイベントがないことを意味します。

> **注記** コンソールは原因を自動確定しません。イベントが見えてもルールを変更することはありません。受け取った事実を表示するだけです。

## 点検で記録すべきこと

点検記録の目的は履歴を残すことではなく、次の人があなたの判断を再現できるようにすることです。以下の表は、点検ごとに最低限記録すべき内容と、それぞれを省略できない理由を示します。

| 記録する内容                         | 記録が必須の理由                                                                             | 記録の書き方                                                                                                           |
| :----------------------------------- | :------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| 時間範囲と環境                       | 窓を変えて比較すると違いを自分で作ってしまい、結論を検証できない                             | UTC の開始終了時刻と環境識別子を明記します。「今日の午前」のような相対表現は書きません                                 |
| アプリケーションとインスタンス識別子 | 同じアプリケーションに複数のインスタンスがあるため、結論は特定のインスタンスに絞る必要がある | アプリケーション識別子とインスタンス識別子を書きます。ホスト名は書きません。ホスト名は関連付けの欄に分けて記載します   |
| 確認した現象                         | 指標名と定義は誤読されやすく、元の記述を残せば事後の解釈し直しを避けられる                   | 指標名に加えて具体的な値や曲線の形を書きます。「少し高い」のような書き方はしません                                     |
| 対応するイベント識別子               | 障害イベントは追跡可能な記録で、識別子があればグラフ上の異常を具体的に紐づけられます         | イベント識別子を記録します。重大度だけでは残しません。イベントがない場合も「当該ウィンドウにイベントなし」と明記します |
| 関連する版または公開識別子           | 公開と適用は別の事象で、識別子があればその時点で有効だった版が分かります                     | 管理型ルールは版識別子と公開識別子を記録します。ネイティブルールはソースのリビジョン番号を記録します                   |
| 実行した操作                         | 操作は現状を変えるため、記録しないと変化が操作によるのか元々あったのか区別できません         | 操作と返却結果を時系列で記録します。結果が不明なものを含めます                                                         |
| 結論と次のアクション                 | 判断を他人が検証でき、次の作業も続けられる必要があります                                     | 結論の根拠となった証拠を明示し、次に何を調べるかを書きます                                                             |

> **注記** 最後の項目の「結果は不明」は省略しないでください。結果が不明な書き込み操作を成功として記録すると、その記録に依拠する以降の推論すべてに、根拠のない前提が混入します。
