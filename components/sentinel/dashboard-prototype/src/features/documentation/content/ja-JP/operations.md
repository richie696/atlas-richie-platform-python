## バックアップすべき対象

バックアップは 3 つに分けて必要です。互いに含まれておらず、1 つをバックアップしても残りの 2 つは復旧できません。

| 対象                         | 含むもの                                                                        | バックアップしないと                                                                           |
| :--------------------------- | :------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------- |
| Console データベース         | アカウント、ロール、ソース登録、バインディング、下書き、版、公開記録、監査      | アカウントも履歴も消え、ルールの公開記録も消えます                                             |
| 配置側の鍵と状態ディレクトリ | 鍵リング、setup-window の状態、ランタイムのロケーションファイル、初回実行ロック | 暗号化されたデータベースのロケーション情報が手当たらなくなり、ソースの認証情報も解読できません |
| 設定センター内のルール       | 現在有効なルールの内容                                                          | ランタイムが読み込むルールがありません                                                         |

> **注記** 監査記録に内蔵の期限切れ機構はなく、クリーンアップコマンドも対象外です。コンプライアンスで長期保管が求められる場合や、この表のサイズを管理したい場合は、Console データベースの外へ自分でアーカイブしてください。

## 復旧演習の進め方

復旧の手順を演習していないなら、バックアップがあるとは言えません。そのまま実行できる演習手順です。

1. 隔離環境にバックアップのスナップショットを用意します。本番で試さないでください。
2. Console データベースを復旧し、起動とログインができることを確認します。
3. 配置側の鍵と状態ディレクトリを復旧し、暗号化されたロケーションファイルを復号できることを確認します。
4. 設定センターのルール内容がバックアップ時点と一致することを確認します。
5. ログイン後、アカウント、ロール、ソース登録、バインディングがそろっているか確認します。
6. 版一覧と公開記録が完全か確認します。
7. テストインスタンスを 1 つ選び、読込観測の経路を再確立できるか確認します。
8. この演習にかかった時間と、どの段階で詰まったかを記録します。

> **注記** 演習で忘れやすいのは鍵と状態ディレクトリです。データベースには含まれませんが、これがないとデータベースのロケーション情報を解読できません。

## 日常的に確認したいこと

次の項目は日常運用で定期的に確認する価値があります。

障害イベントと監査記録は増え続けるため、定期的に確認します。障害イベントの保持期間は明確で、現在の実装は各イベントに 30 日を付与し、Collector の受信時刻から起算します。クリーンアップタスクが一度も実行されていなくても、照会時には論理的な期限切れで期限超過のイベントが除外されます。物理削除は配置側で実行し、コマンドは `sentinel-console incident-events expire` です。現在の UTC 時刻を基準に期限切れの行を削除し、実行後に削除件数を表示します。`expired-incidents=12` の如きです。安全に繰り返し実行できます。このコマンドが削除するのは障害イベントだけで、アカウント、ルール版、公開記録は削除対象外です。コンプライアンスで長期保管が必要な場合は、監査記録と障害イベントをどちらも Console データベースの外へ別途アーカイブしてください。このクリーンアップコマンドはそれらをカバーしていません。アーカイブ後はクリーンアップタスクも通常どおり実行でき、コピーには影響しません。

1. ソース接続のプローブが引き続き使えるか確認します。プローブの失敗は公開に直接影響します。
2. 監視対象がまだ収集され、サンプルが新鮮か確認します。
3. Reporter のハートビートがタイムアウトしていないか確認します。
4. 初期化ウィンドウが閉じているか確認します。
5. ディスク容量とログディレクトリが蓄積していないか確認します。
6. 監査記録を定期的に抜き取り確認し、異常な操作が判別できるか確かめます。

## ヘルスチェックで証明できること

プロセスのヘルスチェックは、そのプロセスがリクエストに応えられるかだけを示します。データベースに接続できるか、設定センターを読めるか、監視経路にデータがあるかは確認しません。

したがって「ヘルスチェックが緑」を「システム正常」とみなすことはできません。経路の健康状態は「接続と収集」タブのプローブ結果で確認します。

| シグナル                 | 証明できること                             | 証明しないこと                                 |
| :----------------------- | :----------------------------------------- | :--------------------------------------------- |
| プロセスのヘルスチェック | プロセスが応答できる                       | データベース、設定センター、監視が正常かどうか |
| ソース接続のプローブ     | いま設定センターへ接続できる               | ルール内容が正しいかどうか                     |
| 監視ソースのプローブ     | いま監視バックエンドを照会できる           | この時間範囲にサンプルがあるかどうか           |
| 読込観測                 | あるプロセスがスナップショットを受け取った | リクエストが実際にブロックされたかどうか       |
