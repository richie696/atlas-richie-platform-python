title: よくある問題の切り分け
summary: 症状から絞り込み、再送と再設定の繰り返しを避けます。
prerequisite: 対象ページの権限があること。管理操作には管理者アカウントが必要なこと。
outcome: 空グラフ、ルール未適用、読み取り失敗、復旧に関する問題を特定できます。

## 症状から探す

左の列で見ている症状を選び、中央の列の順に確認します。

| 症状                           | まず確認する点                                           | よくある原因                                                 |
| :----------------------------- | :------------------------------------------------------- | :----------------------------------------------------------- |
| ルールが見えない               | バインディング一覧、ソース接続、profile                  | 設定位置の記入誤り、認証情報の不一致、profile の不一致       |
| ルールはあるのにブロックしない | リソース名、ウィンドウ閾値、実際に読み込まれた版         | リソース名と計測名が不一致、単位の記入誤り、古い版が有効     |
| アプリケーションの指標が空     | enrollment、mTLS、プロトコル交渉、完了応答とヒストグラム | 証明書の未登録、識別の不一致、一部フィールドのみ報告         |
| ホストの指標が空               | スクレイプ対象、ラベルマッピング、profile、時間範囲      | 対象が up でない、ラベルが一致しない、profile の不一致       |
| イベント一覧が空               | イベントソースが接続されているか                         | イベント経路がそもそも未接続で、障害がないわけではありません |
| 公開の結果が不明               | 実行結果の照会                                           | 再送はせず、まず結果を照会します                             |

## ルールが見えない

次の順に確認します。各段階で原因を 1 種類ずつ絞り込めます。

1. ルールバインディング一覧で、バインディングが存在し、環境とアプリケーション識別子が正しいか確認します。
2. 「接続と収集」タブでソースのプローブが使えるか確認します。
3. 設定センターを読み、読み取り状態が「現在のスナップショット」か「期限切れのスナップショット」か「未読み取り」かを確認します。
4. 設定位置を照合します。Nacos は namespace ID、group、Data ID。Consul は datacenter と完全な KV key です。
5. 業務プロセスが同じ位置を読んでいるか確認します。コンソールと業務プロセスが別の位置を指しているなら、それが最も多い原因です。

## ルールはあるのにブロックしない

設定が存在することは、文字がそこにあることだけを意味します。ブロックには、ルールが読み込まれ、照合され、閾値が正しく計算される必要があります。

1. リソース名と計測名が、大文字小文字、空白、パスも含めて一字一句一致するか確認します。
2. 閾値の単位を照合します。QPS は 1 秒ウィンドウで計算します。ミリ秒と秒を取り違えるのが最も多い誤りです。
3. ルールページで、インスタンスが実際に読み込んだスナップショットの版を確認します。想定した版ではありません。
4. 別のルールが先に照合され、同じリクエストをブロックしていないか確認します。
5. 閾値を超える安定したトラフィックでテストします。短時間の少量のリクエストではたまたま超えないことがあります。

> **注記** Java と Go のアダプターは、検証段階で候補スナップショット全体を拒否します。サポート外のフィールドを 1 つ追加すると、ルールは 1 件も有効になりません。「ルールが突然すべて効かなくなった」を調べる際は、直近の公開の内容を先に見てください。

## 指標が空の場合

指標が空になる原因にはいくつか種類があり、対処も異なります。

1. Reporter の enrollment が済みで、証明書のフィンガープリントがランタイムと一致するか確認します。
2. mTLS で実際に接続が確立し、平文にフォールバックしていないか確認します。
3. プロトコル交渉の成功を確認します。設定に profile 名を書いたことは交渉成功を意味しません。
4. 報告体に完了リクエスト数とヒストグラムの 2 種類のデータがあるか確認します。カウンタだけなら RT は計算できません。
5. 収集端からコンソールまでの区間がつながっているか確認します。

## 書き込み操作の結果が不明な場合

ブラウザのタイムアウトは書き込み失敗の証明にはなりません。サーバーは書き終わっていて、受信確認が返っていないだけの場合があります。

1. まず操作照会インターフェースで、このリクエストの結果を照会します。
2. 結果を確認してから、再試行するかどうかを決めます。
3. 再試行する場合は、同じ冪等キーを使います。キーを変えると別の操作として扱われ、2 回目の書き込みが発生します。
4. 結果が実際に不明な状態なら、その状態のまま底层の事実を調べます。もう一度クリックして試す方法は使いません。

> **注記** 操作照会が「見つかりません」を返しても、操作が起きていないことを意味しません。新しいキーで再生する根拠にもなりません。

## いつ手を止めるべきか

切り分けの価値は除外することにあります。試し続けることではありません。次のシグナルが見えたら、手を止めて事実を確かめてから、次の一手を決めます。

同じページで 2 つの数字が合わないとき、または同じリソースが 2 か所で異なる結論になったときは、操作を続けません。指標の定義の違い（`completed_http_requests` と `attempted_entries`）、時間窓の境界の違い（Console は UTC の半開区間 `[from,to)`）、サンプリングカバレッジの違いで、同じリクエストの集合が別の数字に見ええます。まず各数字がどの観測点・時間窓・定義に由来するかを確認してください。

書き込み操作の結果が不明なときは再送しません。冪等キーを変えると 2 回目の書き込みが発生します。同じキーで照会するのは安全です。照会結果が「見つかりません」でも、操作が起きていないことにはなりません。

設定センターの内容が想定と異なる場合は、両者を並べて照合します。コンソールが記録した版、ソースのリビジョン番号、バイトダイジェスト、正規化ダイジェストと、実際に読んだ内容です。ダイジェストが合わずに、双方の片方が同じスナップショットを見ていないことを示します。照合が終わるまで、どちらの側も変更しないでください。

次の項目はプラットフォーム運用者の担当範囲です。画面上で再試行しても影響は拡大するだけです。暗号鍵と証明書の生成、配布、更新。異なる言語のプロトコル実装の判定が食い違う場合。ランタイムのクラッシュやプロセスの再起動の繰り返し。同一のルール入力が異なる言語のアダプターで異なる結論になる場合。

> **注記** 手を止めることは諦めることではありません。まず確認できた事実を記録します。時刻、範囲、観測点、具体的な数値。それから担当者を呼びます。事実が揃っていれば、問題はたいてい自ずと分類できます。
