## Rust demo が何で、何ではないか

リポジトリの Rust demo は、管理されたランタイムアダプタの検証です。公式の sentinel-core エンジン、Nacos Rust SDK、Consul の文書化された KV HTTP API を使い、ルール・指標・プロトコルの相互運用を検証します。

Alibaba が公式リリースした Sentinel Rust ディストリビューションではなく、本番対応のパッケージでもありません。README には「すべての Sentinel ルール種別とテレメトリ契約的支持を主張するものではない」と明記されています。

| そうであるもの                                              | そうではないもの                       |
| :---------------------------------------------------------- | :------------------------------------- |
| 公式 sentinel-core エンジンで Flow ルールを動かす           | 公式リリースの Rust SDK                |
| Metrics V2 スナップショットを送信し、永続的な受信確認を待つ | 本番級のランタイムアダプタ             |
| 読込観測と公開の受信確認プロトコルを実装する                | すべてのルール種別に対応すること       |
| 管理された環境での再現可能な検証                            | どの環境でも直接デプロイできるサービス |

## 設定とエンドポイント

Rust demo の変数名は前述の 2 つと違って、待ち受けアドレスは HTTP_ADDR を使い、Nacos アドレスは必須で既定値がありません。

| 変数                | 既定値             | 説明                                                   |
| :------------------ | :----------------- | :----------------------------------------------------- |
| HTTP_ADDR           | 127.0.0.1:18094    | 待ち受けアドレス                                       |
| NACOS_SERVER_ADDR   | 既定値なし（必須） | Java の host:port 表記と異なり、ここはアドレス単体です |
| NACOS_DATA_ID       | 既定値なし（必須） | Data ID                                                |
| NACOS_GROUP         | DEFAULT_GROUP      | グループ                                               |
| POLL_INTERVAL_MS    | 1000               | ポーリング間隔。最小 100 ミリ秒                        |
| RULE_PROFILE_ID     | sentinel-rust-v1   | Rust 専用 profile                                      |
| METRICS_CLIENT_CERT | 既定値なし         | PEM のクライアント証明書                               |
| METRICS_CLIENT_KEY  | 既定値なし         | PEM のクライアント秘密鍵                               |

> **注記** Rust demo の /rules は JSON を返しますが、ほかの 2 つの demo はプレーンテキストのキー値行を返します。自動化スクリプトを書く際、3 つの形式が同一だと仮定しないでください。

## 明確にサポートされない機能

次の機能は現在の Rust 対応範囲では実装されていません。不明のフィールドや不明のセマンティクスに遭遇した場合は、無視するのではなく候補全体を拒否します。

| 機能                           | 現在の状態                                                                 |
| :----------------------------- | :------------------------------------------------------------------------- |
| 同時実行数のしきい値           | サポート外                                                                 |
| ウォームアップ                 | サポート外                                                                 |
| 待機キュー                     | サポート外                                                                 |
| 関連および呼び出しチェーン戦略 | サポート外                                                                 |
| クラスタ流量制御               | サポート外                                                                 |
| プロセスの CPU / メモリ指標    | 利用不可としてマークされます。無効化された exporter から推測はしません     |
| Prometheus exporter            | 無効。実際の Flow 経路ではラベルのカーディナリティ不整合でクラッシュします |

> **注記** 不明や未モデル化のフィールドは一律に拒否します。「無視してまず動かそう」とはしません。これは意図的な設計です。無視すると設定が効いているように見えて、実際の保護がまったく効いていないままになるためです。

## 新しい言語を接続するときに実装すべきこと

Java・Go・Rust 以外の言語を使う場合、次の工程を自分で実装して検証する必要があります。demo が存在する意義は、これらの工程の受け入れ基準を固定することにあります。

1. ルール実行器を実装します。リソースの命名、しきい値の計算、拒否時の動作を明確にし、扱えるルールのサブセットを確認します。
2. 設定の監視を実装します。どの形式を読み込むか、不正なスナップショットをどう扱うか、適用済みの前コンテンツを保持するかを決めます。
3. リソースと遅延の計測境界を実装します。どの位置でリクエストを数え、どの遅延を RT として扱うかを決めます。
4. まずトラフィックがない状態で読込と適用を検証し、内容が正しく解析されて読み込まれることを確認します。
5. 次に、応答が固定で遅延を制御できる API で、許可・拒否・RT サンプルを検証します。
6. 最後に、独立した mTLS の身元、プロトコルネゴシエーション、永続的な受信確認、そして Console がこれらの事実を読み戻せるかを検証します。

## Rust demo を動かす

Rust demo のディレクトリ構成・変数名・エンドポイントパスはいずれも前述の 2 つと違います。Java や Go のコマンドをそのまま実行しても通りません。以下の手順は実際の実行順に並べています。

1. demo ディレクトリで cargo run --locked を実行します。demo は NACOS_SERVER_ADDR と NACOS_DATA_ID を読みますが、どちらも既定値がなく、欠けているとプロセスは起動に失敗します。
2. ホストに Rust ツールチェーンがない場合は、コンテナでテストを実行します。docker run --rm -v "$PWD:/work" -w /work rust:1.89-slim cargo test --locked。このコマンドは Nacos・Consul・Collector・ユーザーサービスのいずれにも接続も変更も行いません。
3. 既定の待ち受けは 127.0.0.1:18094 です。アドレスを変える場合は HTTP_ADDR を設定します。host:port 形式を受け付けます。例えば HTTP_ADDR=127.0.0.1:18095 です。
4. ポーリング周期は POLL_INTERVAL_MS で制御します。既定は 1000 ミリ秒、最小は 100 ミリ秒です。100 未満の値を入れてもエラーにはならず、既定の 1000 ミリ秒に戻ります。
5. /rules をリクエストして読込を確認します。Java や Go のようなプレーンテキストのキー値行ではなく JSON を返します。フィールドも 2 つより多く、profile_id、source_revision、membership_complete、member_fingerprints、last_failure が加わります。ネイティブルールでは managed_publication は null です。
6. last_failure が validation_rejected ならスナップショットが検証で拒否され、source_unavailable ならソースの読み取りに失敗しています。この 2 つの値が出現した場合、直前の利用可能なスナップショットが引き続き有効で、破棄されません。
7. 遅延用のフィクスチャは /demo?delay_seconds=0..30 で、単位は秒で 30 にクランプされます。Java と Go の /api/delay?ms= はミリ秒で 2000 にクランプされ、パス名も単位も共通ではありません。
8. /api/hello と /demo はどちらも同じ GET /api/hello リソースに入ります。公開した Flow ルールはこの 2 つの入口を保護します。許可なら 200 の JSON、遮断なら 429 の JSON を返します。

```bash

cargo run --locked
docker run --rm -v "$PWD:/work" -w /work rust:1.89-slim cargo test --locked
```

> **注記** Rust demo は最初の有効なスナップショットを読み込んでから HTTP サービスを開始します。初期スナップショットが読めないか拒否された場合、プロセスは直接終了します。ポートを開いてから再試行を繰り返すことはありません。その後のポーリングで不正なスナップショットが得られた場合は、直前の利用可能なスナップショットを保持し、プロセスは終了しません。
