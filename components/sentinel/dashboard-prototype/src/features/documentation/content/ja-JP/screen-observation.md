この 2 つのページが解いているのは**過程と帰属**の問題です。リアルタイム監視は「今何が起きているか」を見せ、障害分析は「すでに何が起きたか」と「照合できる証拠が何か」を見せます。

## リアルタイム監視ページの 2 つのデータ領域

リアルタイム監視ページにタブはありませんが、同時に 2 つの並行データ領域を表示します。

| データ領域   | 指標                                                                         | 口径                       | 好悪の方向はあるか                             |
| :----------- | :--------------------------------------------------------------------------- | :------------------------- | :--------------------------------------------- |
| プロセス基準 | HTTP QPS、業務 TPS、応答時間 p95、リクエスト拒否率、CPU 使用率、メモリ使用率 | プロセス内で収集           | CPU、メモリ、RT p95 にのみ閾値の根拠があります |
| ホスト基準   | ホスト CPU 稼働率、ホストメモリ使用量、ホストメモリ使用率、1 分間平均ロード  | node-exporter の収集ソース | ありません                                     |

> **注記** ホスト基準の 4 指標には方向の定義がありません。コンソールは「何をもって高とするか」を判断しません。同一ホストのコンテナ指標・プロセス指標と併せて読む必要があります。

## リアルタイムページのコントロール項目

| コントロール   | 取値                                      | 説明                                                                         |
| :------------- | :---------------------------------------- | :--------------------------------------------------------------------------- |
| 指標           | すべての指標 / 単一の指標                 | 切り替えると選択した指標だけを描画し直します                                 |
| インスタンス   | すべてのインスタンス / 単一のインスタンス | ドロップダウンは利用可能な収集範囲を宣言しているインスタンスだけを列挙します |
| 収集範囲       | プロセス / コンテナー / ホスト            | 収集範囲が 2 層未満のとき、このコントロールは無効になります                  |
| 時間範囲の方式 | 現在時刻まで移動 / 固定の過去の時間範囲   | `event` パラメータ付きで入ると固定の履歴ウィンドウに切り替わります           |
| 更新を一時停止 | 一時停止 / 再開                           | このブラウザーによる読み取りだけを制御します                                 |

既定のポーリング間隔は 5000 ミリ秒です。

> **注記** **更新の一時停止は、このブラウザーがデータを読み取るのを止めるだけ**です。バックグラウンドの収集と流量保護は動き続けます。ブラウザーのタブを閉じてもルールが無効になることはありません。

> **注記** インスタンスのドロップダウンに某インスタンスが無いのは、通常そのインスタンスが利用可能な収集範囲を宣言していないためです。システムは別の階層の指標で欠落を埋めることはありません。

## 障害分析ページの 2 欄構成

![障害分析ページ：上部に環境、アプリケーション、時間範囲、インスタンス、イベント重要度、イベント種別の絞り込みがあり、下部に 5 枚の統計カード、左側にイベントタイムライン、右側に選択したイベントの証拠パネル（観測値と閾値、証拠の状態、影響アプリケーション、関連インスタンス、発生時刻）があります。](docs/figures/ja-JP/faults.png "障害分析ページはイベント事実のみを持ち、メトリクスカードはありません。右の証拠は事実の種類に応じて、リソース圧迫または応答時間の観測値と閾値、および公開記録と読込記録を示します。")

左欄がイベントタイムライン、右欄がイベント証跡です。イベントは 4 種類だけで、証拠の中の事実コードから逆向きに導かれます。

| イベント種別 | 事実コード          | 証拠が示すもの                       |
| :----------- | :------------------ | :----------------------------------- |
| リソース圧迫 | `resource_pressure` | 指標名、値、観測した閾値             |
| 応答時間     | `response_time`     | 値（ミリ秒）、観測した閾値（ミリ秒） |
| ルール公開   | `rule_published`    | ルールバージョン番号                 |
| ルール有効化 | `rule_applied`      | ルールバージョン番号                 |

重要度は 3 段階です。重大、警告、情報。

### 統計カードはフィルタの影響を受けない

ページ上部には 5 枚の統計カード（影響アプリケーション、重大なイベント、警告イベント、ルール変更など）があります。どのカードにも同じ一文が付きます。**現在の環境・アプリケーション・インスタンス・時間範囲の全範囲集計。種別・重要度・ページングの影響を受けません**。

> **注記** 統計カードは全範囲の数字です。タイムラインやフィルタ結果はフィルタ後の数字です。2 つの数字が一致しないのは正常であり、不具合ではありません。

### 証拠パネルが提供するもの

イベントを選ぶと、右側に次の項目が表示されます。発生時刻、影響アプリケーション、関連インスタンス、プロセス起動識別子、サーバー受信時刻（システムタイムゾーン）、読み取り時刻（システムタイムゾーン）、元イベント識別子、公開記録識別子、および証拠の状態（証拠が揃っています / 一部の証拠のみ / 証拠を取得できません）。

証拠の状態は飾りではありません。

| 証拠の状態           | 結論として言えることの上限               |
| :------------------- | :--------------------------------------- |
| 証拠が揃っています   | その中の観測値と閾値を引用できます       |
| 一部の証拠のみ       | 受信済みの事実部分だけを引用できます     |
| 証拠を取得できません | 「この事象が発生した」ことだけを知れます |

> **注記** ページには明確にこう書かれています。**時刻が近いだけで因果関係とは限りません**。システムは根本原因を自動確定せず、ルールも自動変更しません。推奨する次の対応（アプリケーションとインスタンスを見るなど）ボタンの有効集合はサーバーが決めるため、その一部しか表示されないことがあります。

## 2 つのページを重ね合わせる

リアルタイム監視で見るのは「起きている最中」、障害分析で見るのは「記録された過去」です。重ね合わせるには、環境・アプリケーション・時間範囲の 3 条件が完全に一致している必要があります。

1. リアルタイム監視ページで、現在の時間範囲の方式と選択中のインスタンスを確認します。
2. 曲線が転折した大まかな時刻を覚えておきます。
3. 障害分析ページに切り替え、同じ環境・アプリケーション・範囲で絞り込みます。
4. タイムラインで同じ時刻付近の記録を探します。
5. 証拠を開き、リソース圧迫・応答時間・ルール変更のどれかを確認します。
6. リアルタイム監視ページに戻り、同じインスタンスで現在の曲線が回復したかを確認します。

> **注記** 障害分析のタイムラインとリアルタイム監視の曲線は 2 つの別々の読み取り値です。前者は Collector が永続化したイベント記録、後者はリアルタイムにポーリングした指標です。両者の時刻を合わせる際には、収集と報告の遅延分を空けてください。

## イベント一覧に含まれないもの

障害分析ページに**メトリクスカードはありません**。QPS、RT、CPU の曲線は描かず、イベント事実と証拠のフィールドだけを示します。

> **注記** 指標の曲線を見たい場合はリアルタイム監視ページへ、イベントと証拠を見たい場合は障害分析ページへどうぞ。このページに曲線がないのは欠陥ではなく、分担です。
