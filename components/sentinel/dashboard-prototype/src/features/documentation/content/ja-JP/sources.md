## ソースとバインディングは別の 2 つのこと

ソース登録は「この設定センターへどう接続するか」に答え、ルールバインディングは「このアプリケーションのルールはどこにあるか」に答えます。両方が揃う必要があり、どちらか一方でも欠けるとルールを読み取れません。

ルールバインディングは、環境・アプリケーション・ルール種別・設定場所の 4 要素で構成され、加えてランタイム profile がこのバインディングで許可するフィールドを決めます。サービスとコンソールは同じ設定場所を指している必要があります。これが「ルールが読めない」原因として最も多いものです。

ブラウザは Console API 経由でソース登録・公開先入力・状態確認だけを行い、Nacos / Consul へ直接接続しません。バックエンドの provider アダプターが認証情報の解決、設定の読み書き、独立した読み戻しを担当します。Runtime は設定センターからルールを読み、稼働の事実を Collector に報告します。これらは別の経路です。

| 設定センター | 設定場所のフィールド         |
| :----------- | :--------------------------- |
| Nacos        | namespace ID、group、Data ID |
| Consul       | datacenter、完全な KV key    |

## 3 つの認証方式

ソース登録時に認証方式を選べます。アドレスにパスワードやトークンを載せないでください。

| 方式                     | 意味                                                                   | 向いている相手                                               |
| :----------------------- | :--------------------------------------------------------------------- | :----------------------------------------------------------- |
| なし                     | 宛先で認証が不要                                                       | ローカルまたは社内テスト環境                                 |
| 直接資格情報             | コンソールがアカウントとパスワードを直接保持し、暗号化して保存する     | 単一のコンソールインスタンスでソースを管理する場合           |
| デプロイ側資格情報の参照 | コンソールは参照だけを保存し、実際の資格情報はデプロイ側から注入される | 複数インスタンス、または資格情報のローテーションが必要な構成 |

> **注記** 資格情報の参照は、鍵管理サービスの導入を強制するものではありません。必要になるのは、資格情報をコンソール自身が保管しないことだけです。

## ソースを 1 件登録する

システム管理の「接続と収集」タブで登録します。登録は接続の方法を記録するだけで、設定センターの内容は一切変更しません。

1. システム管理を開き、「接続と収集」タブのままにします。
2. プロバイダ種別で Nacos または Consul を選び、サービスアドレスを入力します。
3. 認証方式を選び、対応する情報を入力します。
4. 接続をテストします。失敗したら、まずプローブ結果の理由を確認し、次にネットワークホワイトリストと証明書を確認します。
5. 保存します。保存するとソース一覧に現れ、後続のバインディング作成で選択できます。

## ルールバインディングを 1 件登録する

ルールページで登録します。バインディングは、コンソールがどこで読み、どこで書き、どの形式のルールを書き込めるかを決めます。

1. ルールページを開き、ルールバインディング一覧で「ルールセットのバインディングを登録」をクリックします。
2. デプロイ環境とアプリケーション識別子を選びます。一覧が空の場合は、初回設定時の識別子を直接入力できます。
3. ルール種別を選びます。バインディングは種別ごとに分かれ、種別ごとに独立したバインディングです。
4. 設定ソースを選び、上の表に従って設定場所を入力します。
5. ランタイム profile を選びます。公開できるのは profile が対応するフィールドだけです。
6. 保存するとルール一覧にこのバインディングの項目が現れ、設定センターを読み取れます。

> **注記** profile は機能の上限を決めます。画面のフォームに存在するフィールドでも、現在のバインディングが公開できるとは限りません。公開前の検証で拒否されますが、より良いのは入力時に profile のサブセットに限ることです。

## 空配列・不在・失敗の違い

この 3 つは画面上の見え方が異なりますが、初心者はよく混同します。区別できれば調査時間の半分が省けます。

| 読み取った状態       | 意味                                             | 次の手                                                                               |
| :------------------- | :----------------------------------------------- | :----------------------------------------------------------------------------------- |
| 空配列               | この場所は確かに存在し、中身はルール 1 件もない  | 正常な状態。最初のルールを書き始められます                                           |
| 宛先なし             | この場所は設定センターに存在しない               | 設定場所の誤りか、そもそも設定センターに未作成かを確認します                         |
| 権限なし / 接続失敗  | 読み取れない                                     | 「ここにはルールがない」のではなく、資格情報とネットワークを確認します               |
| 前回の成功内容を保持 | 今回は読み取りに失敗し、前回の内容を表示している | まず接続を直し、そのうえで再読み取りします。現在表示されている内容は現状を表しません |

> **注記** 公開は全体の置換であり、差分パッチではありません。つまり「0 件を読み取った」と「読み取れなかった」は結果が大きく異なります。前者は今クリアした可能性があり、後者は設定センターが停止している可能性があります。

## ソースに接続できないときの調査順序

接続失敗の原因は層ごとに分かれています。順番に調べた方が繰り返しの再試行より速いです。次はアドレス、設定場所、資格情報、ネットワークホワイトリスト、信頼根、最後に接続の再テストです。

1. まずアドレスの形式を確認します。サービスアドレスは http か https のみで、ユーザー情報・クエリ文字列・フラグメントを含めません。ホスト名は正当な DNS 名か、正規表記の IP アドレスのどちらかです。パスワードやトークンをアドレスに入れることはできず、認証方式で伝えます。
2. 次に設定場所を確認します。Consul は datacenter と完全な KV key、Nacos は namespace ID・group・Data ID の 3 段です。設定場所が間違っていても接続テストは通りますが、読み取り時に宛先が見つかりません。「接続できるのにルールが読めない」原因の主要部分です。
3. 資格情報を確認します。認証方式は、なし・直接資格情報・デプロイ側の資格情報参照の 3 つです。直接資格情報は Console バックエンドが保持して暗号化保存し、誤れば認証失敗になります。参照方式はデプロイ側から注入し、接続時にバックエンドが解決して使います。ブラウザへ実値を読み戻したり、その資格情報で設定センターへ直接接続したりしません。
4. ネットワークホワイトリストを確認します。ソース宛先ホワイトリストの形式は プロバイダ|ホスト名|セグメント,セグメント|ポート,ポート で、複数項目はセミコロン区切りです。プロバイダ名とホスト名は実際の宛先と一致し、ポートは許可リスト内、セグメントはデプロイ側の送信元アドレスを網羅している必要があります。
5. TLS の信頼根を確認します。プライベート CA で発行されたソースには PEM CA bundle の設定が必要で、ないとハンドシェイクが失敗します。信頼根を設定したからって検証を省略できるわけではなく、証明書検証とホスト名検証は引き続き有効です。
6. 最後に接続を再テストします。プローブが返す失敗理由は有限の集合で、任意の例外テキストは含まれません。ソースチェックは connection、authentication、unsupported を返し、システム管理の接続ビューは network、authentication、unsupported、not-configured、no-probe を返します。どちらのグループを見ているかを確認してから、原因ごとに調査します。

| 確認項目                 | 確認方法                                                                                | 通らなかった場合                                                                                                                   |
| :----------------------- | :-------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------- |
| サービスアドレスの形式   | http または https のみ。ユーザー情報・クエリ文字列・フラグメントを含まない              | パスワードやトークンをアドレスから削除し、認証方式で資格情報を渡す                                                                 |
| 設定場所                 | Consul は datacenter と完全な KV key、Nacos は namespace ID・group・Data ID             | 接続テストは通るが読み取りが失敗する場合は、まずこの項目を照合します                                                               |
| 資格情報                 | なし・直接資格情報・デプロイ側資格情報の参照の 3 つから 1 つ                            | 直接資格情報の誤りは認証失敗。参照の場合はデプロイ側の注入を確認します                                                             |
| ソース宛先ホワイトリスト | プロバイダ\|ホスト名\|セグメント,セグメント\|ポート,ポート で複数項目はセミコロン区切り | プロバイダ名・ホスト名・ポートのいずれかが一致しなければ拒否されます                                                               |
| TLS 信頼根               | プライベート CA には PEM CA bundle の設定が必要                                         | 信頼根が欠けているとハンドシェイクが失敗します。補っても証明書とホスト名の検証は維持されます                                       |
| テスト結果の失敗理由     | ソースチェックは connection、authentication、unsupported のいずれか                     | connection はネットワークとホワイトリスト、authentication は資格情報と信頼チェーン、unsupported はプロバイダとパラメータを調べます |
