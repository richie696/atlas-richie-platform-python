# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. All Dashboard application source under `src/` must use TypeScript (`.ts` / `.tsx`); `npm run typecheck` is a required verification step. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run typecheck`, `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Atlas Richie Sentinel design decisions

- Login layout (2026-10-24): keep the Atlas Richie Sentinel brand left-aligned; center the login heading and introductory copy in every supported language. Keep the password reveal icon inside the password field, allow about 30px between the password field and login button, place the documentation link below the form, and provide a shared public language selector at the page's upper right. Preserve password-manager autocomplete and accessible, keyboard-operable reveal behavior.

- Account lifecycle (2026-10-24): every authenticated avatar menu exposes own-password change; admins additionally get account maintenance. Account rows expose role, enable/disable, admin reset-password and delete. Reset needs one new password, revokes all target sessions and does not enable a disabled account. Delete is a tombstone that hides directory/detail while retaining username and audit/publication references. Built-in accounts are protected from admin mutations; self reset uses the old-password-verified own-password flow and self deletion is blocked. Reuse DialogFrame; never retain plaintext credentials in operation receipts or browser persistence.

- The 2026-09-14 selected visual baseline is the instance matrix with an adjacent selected-instance trend panel; use the release-analysis visual treatment for chart grids, annotations and before/after comparisons.
- The fleet-wide overview is a separate page using the release-analysis information hierarchy. It drills down to the application/instance page.
- The six top-level pages are 总览、应用与实例、规则、实时监控、故障分析、系统管理. Each page must answer a distinct operational question.
- This folder contains the Sentinel Dashboard React frontend. Demo mode uses labeled synthetic data and must not contact Nacos, Consul, real databases, or claim that a rule was published; live mode may target only an explicitly configured, controlled Console API. The Python per-process diagnostic dashboard and the independent control plane remain separate services.
- Permissions stay conceptually limited to metrics:view and rules:write; no tenant hierarchy or approval flow. Differentiate host/container/process/application metric scopes; never infer TPS from HTTP QPS.
- React 19 is the selected implementation. Use `@richie696/react-framework` and `@richie696/react-framework-react` for cross-cutting mechanics; product routes, rules, metrics, i18n, UI and theme stay in this application. The frontend has explicit Mock/live HTTP assembly; this does not imply that the Python Console or production data authorities are complete.
- Sentinel Dashboard is a management control plane, not only a configuration-center editor. On a first start without persistent storage, only `#/setup` and health checks are available: the in-product setup flow configures protected system storage, creates the built-in admin without a default password, registers an initial Nacos or Consul rule source, and then opens login/control-plane APIs. Setup is a one-time, server-governed surface: after successful initialization the server closes the initialization window, rejects repeated setup access, the client redirects any `#/setup` deep link to `#/login`, setup has no “back to login” action, and login has no setup entry point. The configuration center remains authoritative for active rules; the Dashboard relational database owns accounts, roles, audit, drafts, version plans, publishing records and source registration; long-term metrics/events remain a separate future storage concern.
- PostgreSQL and MySQL are the production control-plane database choices; SQLite is limited to local, single-process development. The backend must hide each database's driver, SQL dialect, migration lock, and error behavior behind its persistence adapter rather than leaking vendor branches into account, audit, version, or publishing workflows.
- Follow the generic `modern-react-ui-design` skill and `richie696-react-library/docs/REACT_ENGINEERING_STANDARD.md` for UI/UE, code ownership and the project skeleton. The separate `RICHIE_FOUNDATION_USAGE.md` explains this application's installed foundation APIs. Keep Sentinel-specific design and migration decisions in this repository.
- `src/core/styles/index.scss` is the sole application stylesheet entry. Structural tokens, the selected dark skin, reset and necessary Astryx adaptations have separate owners. All shared/feature presentation rules have moved to owned `*.module.scss`; `_legacy.scss` and the original `styles.css` are removed, and must not be restored as competing stylesheets. Semantic hooks remain for existing integration/visual tests and bounded cross-component presentation slots; generated classes provide the actual local ownership. Use `scopedClasses` to compose owned modules without rebuilding arrays in render. New styles must belong to a component or feature, with skin values in the `--sentinel-*` namespace. Astryx markup dependencies belong only in the audited adapter. Use `tests/visual/capture-baseline.mjs compare` to prove rendered output, not just DOM/build results. A theme extension hook does not imply another skin or a working theme switch has been delivered.
- The React skeleton is active: `src/app/` owns application composition, hash routing and shell; `src/features/` owns the page capabilities and their private models/state/ui; `src/shared/` owns only real cross-feature UI contracts. The root `src/App.tsx` is a compatibility export for the existing Vite entry. Features import each other only through an explicit public entry (`features/<name>/index.ts`), never by deep path.
- Engineering sequence confirmed on 2026-10-07: finish frontend responsibilities, state/workflow contracts, component/SCSS boundaries and complete page interactions; keep all page traffic on the same Console HTTP adapters in mock and live modes. Mock/live selection remains in runtime assembly and HTTP interception, never in page/store branches. Then implement and integrate the independent Python Console against the generated/approved contracts. Do not contact real configuration centers or initialize real user databases during local work. Preserve the approved visual baseline; code existence/build success does not prove rendered or live functionality.
- Gateway replacement status: the old FixtureGateway, synchronous pages/exports, and unmounted HTTP draft were retired from the current source; feature-owned HTTP adapters now use the application Console transport. Mock interception is active in the demo profile and production live-only artifacts exclude mock code. This does not mean every mock command is fully stateful, that all page workflows are accepted, or that Python/live E2E has passed; use the sole progress checklist for those boundaries. Do not reintroduce the old gateway as compatibility code or a test double. Logical tests may use minimal feature-Port doubles; application mock mode intercepts the same HTTP requests used in live mode.
- UI baseline: use Astryx Core for accessible primitives and Nivo Line (MIT) for charts; do not introduce Astryx canary chart packages or paid components. Astryx supplies the rendering layer only — it does not own Sentinel's business model, rule forms or page layout.
- Observation degradation: a missing/failed telemetry or observation-catalog read must not blank an entire route. Keep the page title, filters and unrelated content visible; show a concise translated status near the top and render affected metric/event panels as empty/unavailable, never as zero or sample data. Rules and system-management capabilities must not be hidden just because runtime metrics are unavailable; any necessary environment/catalog dependency must be shown as a local limitation and should not masquerade as a metrics failure.
- Modal baseline: use the shared `src/shared/ui/DialogFrame.tsx` for dashboard dialogs. Feature dialogs provide only their body content and actions; the frame owns Astryx Dialog + Layout anatomy, sizing, scrolling, focus and dismissal behavior. The visual treatment is a compact Sentinel navy card with a restrained blue border and dimmed/blurred backdrop, not Astryx's neutral gray showcase surface.
- Form and action layout (2026-10-24): search/filter controls should form one compact, aligned toolbar with a dedicated auto-width action area; avoid placing a lone full-width submit button on a new row. Constrain search and source selectors to the information they represent, give form sections and dense card bodies (tables, pagination, editors) consistent inset spacing, and keep helper/restriction text outside button groups. Registry panels group refresh and add/register actions together in the panel header and use one consistent refresh label. Buttons must keep their labels on one line and must not shrink into awkward widths; responsive layouts may wrap the action group as a unit when space is insufficient.
- Rules-page information hierarchy (2026-10-24): make the rule catalog the default task; separate runtime application status and binding management into URL-restorable sections; group editing, saved drafts, versions/publications, and recovery plans under rule maintenance, with one workflow surface visible at a time. Keep configuration-center reads distinct from runtime acknowledgements, and show historical process observations only when requested. Do not stack every rule subsystem as one long default page.
- Validation cadence: group related edits into one coherent change slice, then validate once at that slice boundary rather than rerunning regression after every file. For routine frontend slices run `npm run check:fast` plus only the affected focused logic/HTTP tests; expand to a whole suite only when the change crosses its ownership boundary. Run `npm run check:milestone` only when the non-browser milestone gate is useful; ordinary commits and PRs use the fast gate. Defer the complete browser E2E and real-backend end-to-end journey until all planned implementation is complete; use Codex's in-app browser then, and never launch Chrome, Edge, or CDP. Report focused checks, IAB observations, milestone checks, and real-backend E2E as distinct evidence. Follow [TESTING_CADENCE.md](docs/TESTING_CADENCE.md) for triggers and proof boundaries.
