## 1. 目标与边界

中文
----

- 任何 ``asgiref.sync_to_async`` / ``nest_asyncio`` / 线程池共享 loop
  (M6.7 决策 1.x 不允许)

## 2. 测试架构

### 2.1 进程拓扑

```
┌──────────────────────────────────────────────────────────────────┐
│ pytest 主进程 (test driver)                                      │
│                                                                  │
│  ┌──────────────┐  ┌─────────────────┐  ┌─────────────────┐     │
│  │ TCP Proxy    │  │ Cluster Server  │  │ Client A        │     │
│  │ (subprocess  │  │ (subprocess,    │  │ (subprocess,    │     │
│  │  P1, killable│  │  P2, real port) │  │  P3, RTSA)      │     │
│  │  for fault   │  │                 │  │                 │     │
│  │  injection)  │  │                 │  │                 │     │
│  │              │  │                 │  │                 │     │
│  │  listen on   │◀─┤ listen on       │  │ talk to proxy   │     │
│  │  port P      │  │  port S         │  │  port P         │     │
│  └──────────────┘  └─────────────────┘  └─────────────────┘     │
│         ▲                       ▲             │                 │
│         │                       │             │                 │
│         └─────────P=S proxy link─┘             │                 │
│         │                                     │                 │
│  ┌──────────────┐                              │                 │
│  │ Client B     │──────────────────────────────┘                 │
│  │ (subprocess  │                                                │
│  │  P4, RTSB)   │                                                │
│  └──────────────┘                                                │
└──────────────────────────────────────────────────────────────────┘
```

- **TCP Proxy** (subprocess P1): 可控 kill/restart, 模拟网络断连/分区
- **Cluster Server** (subprocess P2): 真实 ``StandaloneTokenServer`` 进程, 跑在
  port S
- **Client A / B** (subprocess P3 / P4): 真实 ``RemoteTokenService`` 进程, 各自独立
  ``instance_id`` + ``startup_epoch``
- **Test driver** (pytest 主进程): 跑 pytest, 用 ``multiprocessing.Queue`` 跟
  Client A/B 通信, 用 ``subprocess.Popen.send_signal`` 控制 Proxy + Server

### 2.2 进程间通信 (IPC) 协议

**Client Agent 协议** (跟 driver 用 multiprocessing.Queue):

```python
# Driver → Agent
{"cmd": "acquire", "resource": "/api/v1/users", "permits": 1.0, "deadline_ns": 5000000}
{"cmd": "release", "token": <token dict>}
{"cmd": "aclose"}
{"cmd": "shutdown"}  # exit

# Agent → Driver
{"result": "acquire", "ok": True, "response": <TokenResponse dict>}
{"result": "acquire", "ok": False, "error": "ClusterServerError", "message": "..."}
{"result": "release", "ok": True}
{"result": "shutdown", "ok": True}
```

- Token / TokenResponse 用 ``dataclasses.asdict`` 序列化, **不**用 pickle
  (跨进程 dataclass 不可靠, 1.0 简化用 dict)
- 失败: 序列化错 / 连接错 / 协议错都走 ``{"ok": False, "error": ..., "message": ...}``
- Agent 进程: 阻塞 loop, 等命令 → 执行 → 返结果 → 继续

### 2.3 Network Fault Injection

**Proxy-based 故障注入** (1.0 简化, 不引入 toxiproxy / docker network 依赖):

```python
class TcpProxy:
    """简单 TCP forwarder, killable for fault injection."""
    
    def __init__(self, listen_port: int, target_host: str, target_port: int):
        ...
    
    async def start(self) -> None: ...   # start forwarding
    async def stop(self) -> None: ...    # pause forwarding (close listener)
    async def kill(self) -> None: ...    # hard kill (模拟网络断)
    async def restart(self) -> None: ... # 重新监听, 恢复转发
```

故障模式:
- **网络不可达**: kill proxy → Client 连接被 RST → 走 ``ClusterFailurePolicy``
- **网络分区**: kill proxy + 持续 5s → 验证 quota 不超发 (Client 不可达期间
  Server 端 lease TTL 自动释放, 配额恢复; Client 端因 ``_acquire_with_retry``
  retry 失败走 FAIL_CLOSED deny)
- **请求未送达**: proxy 收到包但延迟 60s 再转 (模拟"送达但响应丢失")
- **cancel**: 调 ``rts.aclose()`` 中断 (M6.3.4 暴露的 async API)

### 2.4 Server 进程启动

config = ClusterTokenConfig(

### 3.2 M6.4.2 — FAIL_CLOSED 跨进程并发争抢

**场景**:
- max_permits = 5.0
- Agent A 跟 Agent B 同时各发 10 个 acquire (各 0.5 permits)
- 验证: 跨进程累计 grant 总量 = 5.0 (Server 端额度, 不超发)
- 全部 release 后, 配额恢复到 5.0
- 再 acquire 5 个 grants 成功 (无 double-charge)

**Test ID**: SEN-CLUSTER-001(part:fail-closed-quota)

### 3.3 M6.4.3 — Server crash 与恢复

**场景**:
1. Agent A acquire 1.0 permits (grant)
2. Server 进程被 kill -9 (Server 内存 state 丢失)
3. Server 重新启动 (新进程, 新 state, 配额重置)
4. Agent A 重新 acquire: 仍能成功 (新 Server 接受新 lease)
5. **关键**: 旧 lease 不在新 Server 状态里, 不影响新分配

**Test ID**: SEN-CLUSTER-001(part:server-crash)

**已知**: M6.3 设计 §8 接受 "Server 重启 lease 失效", 验证这个行为.

### 3.4 M6.4.4 — 网络分区 + deadline

**场景**:
- max_permits = 5.0
- Agent A 持有 2 leases (2.0 permits used)
- 模拟 3 类网络故障:
  a. **请求未送达**: proxy kill 后 Client A 发 acquire, 走 3 次 retry + policy → DENIED
  b. **送达但响应丢失**: proxy 收到后延迟 60s 转 (大于 deadline), Client 端 deadline
     超时 → 走 policy
  c. **cancel**: 调 ``rts.aclose()`` 中断, Client 端 acquire 抛 ``ClusterServerError``
- 验证: 任意场景下, Server 端配额不超发 (即使 Client 失败, Server 端 grant 也
  不残留; 因为没真收到 grant, Server state 干净)
- 验证: 同 request_id 重试不双扣 (idempotency cache 5 min TTL)

**Test ID**: SEN-CLUSTER-001(part:network-partition)

### 3.5 M6.4.5 — owner restart / stale-owner fencing

**场景**:
- Agent A (epoch=0) acquire 1 lease
- Agent A 进程被 kill
- Agent A 重新启动, 同样 ``instance_id``, 但 ``startup_epoch=1`` (新 process 重新生成)
- Agent A 用**新 epoch=1** 调 release 旧 lease (虽然 lease_id 是 epoch=0 时期签的)
- 验证: Server 端返 ``STALE_EPOCH`` 错误码, Client log warn 静默, 配额不释放
  (旧 lease 在 Server 端自然 TTL 到期自动清理)

**Test ID**: SEN-CLUSTER-001(part:stale-epoch)

**已知**: M6.3-CLUSTER-TOKEN-DESIGN §4.4 决策, owner_epoch fencing 防旧 epoch
迟到 release / renew 干扰新 epoch.

### 3.6 M6.4.6 — 规则 version 切换

**场景**:
- 初始 max_permits=5.0 (来自 RuleSource v1)
- Agent A 持有 3.0 permits (3 leases)
- RuleSource v2 推送新配额 max_permits=10.0
- 验证:
  - 旧 lease 继续生效 (v1 期间签的, 不会被强制回收)
  - 新 acquire 用 v2 配额 (剩余 7.0 permits, 能 acquire 7 个 1-permit grants)
  - 配额上限变更不双扣
  - audit 事件: ``RULE_VERSION_CHANGED`` (用 metrics 计数, 不冻结 wire schema
    — M6.5.7 后冻结)

**Test ID**: SEN-CLUSTER-001(part:rule-version)

### 3.7 M6.4.7 — FAIL_OPEN / LOCAL_FALLBACK 降级

**场景**:
- 配 ``ClusterFailurePolicy.FAIL_OPEN`` for `/r1`
- Server 进程 kill
- Agent A 调 acquire → 走 FAIL_OPEN → 返 ``TokenResponse(FAIL_OPEN)`` + stub token
  (``lease_id=None`` 标记)
- 验证: 每次放行都有 metrics counter 增量 (``acquire_fail_open``)
- Server 重启
- Agent A 再调 acquire → 恢复正常 (走 REMOTE_GRANTED)
- 配 ``ClusterFailurePolicy.LOCAL_FALLBACK``, 重复上述场景 → 返
  ``TokenResponse(LOCAL_GRANTED)`` (从 LocalTokenService)

**Test ID**: SEN-CLUSTER-001(part:degrade-policy)

## 4. 关键技术决策 (sign-off 前等 owner confirm)

### 4.1 进程间通信: multiprocessing.Queue vs subprocess.Popen

**决策**: ``multiprocessing.Process`` + ``multiprocessing.Queue``

**理由**:
- 1.0 简化: 不用管 stdin/stdout 序列化, Queue 内置多进程安全
- 比 subprocess.Popen 启动快 (没 Python 解释器二次启动)
- 缺点: 只能在 fork 进程用, 跨平台 Windows 限制 — 1.0 接受 (CI 跑 Linux/macOS)

### 4.2 Token / TokenResponse 序列化: dict vs pickle

**决策**: ``dataclasses.asdict`` → JSON 字符串 → Queue

**理由**:
- 跨进程 dataclass 不可靠 (字段在 Client / Server 端可能不一致)
- 1.0 dataclass 都是 frozen + 简单类型 (str / int / float / None), dict 序列化足够
- 不用 pickle: 反序列化安全性 + 跨语言兼容

### 4.3 Network Fault Injection: TCP proxy vs docker

**决策**: 自己写简单 TCP proxy (subprocess, 200 行)

**理由**:
- docker network 故障注入需要 docker-in-docker, 1.0 简化不引入
- toxiproxy 是独立服务, 1.0 简化不引入
- 自己写 TCP proxy 控制在 200 行内, 0 3rd-party 依赖

### 4.4 Server 启动: Standalone vs Embedded subprocess

**决策**: ``StandaloneTokenServer`` 跑 subprocess (via CLI ``python -m``)

**理由**:
- "Server 在独立进程" 是 M6.4 的核心验收, 必须真 subprocess
- CLI 入口是 1.0 公开 API (M6.3.5 已实施)
- 配 JSON config 文件 (临时生成)

### 4.5 跳过 toxiproxy / docker network / iptables

1.0 简化: 只用 TCP proxy. 复杂网络仿真 (带宽限制 / 丢包率 / TCP 重置) 留 M6.4.x future.

## 7. 风险 / 阻塞

- **跨 pytest-asyncio loop**: Agent subprocess 各自独立 event loop, 不跟 pytest
  主 loop 冲突 (跟 M6.3.4 contract test 一样的 thread-based 模式)
- **Test 慢**: 多进程 + 真实网络往返, 单个 test 2-5s; 全套 7 子任务 + harness 估
  60-90s. pytest 加 `-x` + 单独跑子任务 OK
- **macOS 端口复用**: SO_REUSEADDR + bind ephemeral 端口, 1.0 简化不固定
- **Python 3.12 multiprocessing fork**: 默认 macOS 走 spawn (3.14 才默认 fork),
  每个 Agent 启动 ~0.5s, 可接受

## 8. 不在 M6.4 范围

- 多机多机房
- 多个 Token Server 节点 + leader election
- Server 进程内 store 持久化
- 跨语言 Token Client (Java → Python 集群)
- HAProxy / Envoy 集成
- Wire protocol V2 冻结 (M6.5.x 之后)
