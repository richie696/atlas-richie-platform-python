## 1. 背景与动机

PLANNING §M6.5 Reporter 通道需要一个**跨语言 / 跨进程 / 版本化**的稳定事件
envelope, 让:

- M6.1 内部 `RuleSourceActivation` fact (C 层私有 frozen dataclass) 走
  Reporter 通道给控制面
- M6.5 健康 / 指标事件 (`RULE_SOURCE_STALE` / `RULE_SOURCE_DEGRADED`) 在
  同一父协议下表达
- 业务执行事件 (`RULE_APPLIED` / `RULE_BLOCKED` / `RULE_FAILED`) 上报到
  Collector 做聚合

**M6.1 阶段明确不冻结 envelope** (M6.1.0b sign-off v3 决策 2):
"跨扩展可观测事件名由 M6.5.7 冻结后经 Agent Reporting 通道消费, M6.1
阶段**不**预设任何字符串常量, 也**不**冻结任何跨语言 wire schema."

**M6.5.7 之前** 所有 event_kind / wire field 都是 Python 内部约定, 不能跨
进程 / 跨语言消费。

## 2. 业务能力与边界

### 2.1 业务能力 (SRP)

**唯一职责**: 冻结 Agent Reporting 通道的 **事件 envelope schema V1**, 包括:

- 8 个 envelope 字段 (protocol_version / event_kind / event_payload /
  instance_id / startup_epoch / sequence / captured_at / received_at)
- 6 个 V1 event_kind 字符串常量 + per-kind frozen dataclass payload
- V1 兼容性矩阵 (添加 optional field 走同 major, 移除 / 改语义走 V2)
- 子协议挂载点 (per-kind payload schema 独立 ADR)

### 2.2 业务边界

- **核心契约层** (`docs/protocols/AGENT_REPORTING_PROTOCOL.md`): 冻结
  envelope schema + event_kind 枚举 + 兼容性矩阵, **不**定义 transport
  (gRPC / HTTP / 自定义) — transport 由 M6.5.1 / M6.5.2 决定
- **不**做 "通用事件总线" 抽象, 只挂 Reporter 自己的格式
- **不**在 Python 内部 `dataclass` 里硬塞跨语言 wire 字段 (Python 投影
  层 `atlas-richie-contracts` 包内, **不**污染主包 `atlas-richie-sentinel`)

### 2.3 数据归属

| 字段 | 写入方 | 服务端权威 | 用途 |
| --- | --- | --- | --- |
| `protocol_version` | Reporter | — | V1 字符串 `"atlas-richie.reporting/v1"` |
| `event_kind` | Reporter | — | 字符串常量 (枚举), 决定 payload schema |
| `event_payload` | Reporter | — | per-kind frozen dataclass 序列化 (JSON) |
| `instance_id` | Reporter | — | Reporter 实例唯一身份 (UUID) |
| `startup_epoch` | Reporter | — | 单调递增, 进程重启后从 0 重新计; 用于 Collector 去重旧 epoch 迟到数据 |
| `sequence` | Reporter | — | 单调递增, 同 (instance_id, startup_epoch) 内连续; 用于缺口检测 + 乱序排序 |
| `captured_at` | Reporter | ❌ | Reporter 进程本地 UTC clock 写入, **仅供诊断** (乱序 / 缺口), **不**做服务端权威 |
| `received_at` | Collector | ✅ | Collector 写入, 聚合 / 排序 / 跨进程比较的**唯一**权威字段 |

**关键约束**: `captured_at` 与 `received_at` **必须分开**, 不得合成单一
`capture_time` 字段。原因: server-authoritative 与 本地 UTC 互相矛盾,
跨语言无法解释 (Python `datetime.now(tz=UTC)` 与 Go `time.Now().UTC()` /
Java `Instant.now()` 都用 epoch microseconds, 但格式化和 timezone 序列化
不互通; 用 server-authoritative 字段作为唯一权威消除歧义)。

## 3. 同步能力 vs 异步事实 (DIP)

### 3.1 同步能力请求 (M6.5.5 认证 / 配置)

- "拿 OAuth client credential" → **同步**, token renewal 走 credential
  provider 状态机
- "拿 transport 选型" (HTTP / gRPC) → **同步**, M6.5.1 / M6.5.2 决策

### 3.2 异步事实响应 (envelope 通道)

- "Reporter 上报某条 event" → **异步**, Collector ack 独立 (sequence 缺口
  状态机)
- "Collector 拒绝 / 校验失败" → **异步**, Reporter 走 overflow policy
- "进程间订阅事件" → **异步事件订阅**, 跨进程边界必须有明确投递语义

### 3.3 envelope 不参与准入决策 (PLANNING §M6.5 数据边界)

> "Reporter 通道不参与每次请求的准入决策"
> 严禁业务请求和响应内容、用户身份、认证材料、任意日志或完整规则正文

## 4. 模式候选 (OOP 守门)

### 4.1 候选: 稳定契约 (Port / Schema Registry)

- **位置**: `docs/protocols/AGENT_REPORTING_PROTOCOL.md` 是跨语言 Port,
  Python / Go / Java / Rust 各自实现, 共享 schema
- **为什么**: 跨语言 wire protocol 不能用 Python `Protocol` (M6.1.0b
  决策 2 明确), 必须用 JSON Schema / Protobuf 等 language-neutral 描述
- **当前会发生的问题**: 跨语言 event 上报没有稳定 schema, 任何语言
  实现都自由发挥, 后果是 1.x 收口后无法跨进程 / 跨语言消费
- **设计**: V1 schema 冻结在 markdown spec, 配 JSON Schema 描述
  (machine-readable, 跟 spec 同 source-of-truth)
- **收益**: 1.x 末所有语言 SDK 实现都遵循同一 schema, 跨语言互操作
- **误用防护**: V1 不可破坏性, schema 变更走 V2+ 独立 ADR + major bump
- **验证**: 跨语言 contract test (Python 序列化 / 反序列化 round-trip,
  Go / Java SDK mock 跑同 spec)

### 4.2 候选: 冻结 per-kind event_payload frozen dataclass

- **位置**: Python 投影 `atlas-richie-contracts` 仓内 (跟主包隔离)
- **为什么**: Python `dict[str, Any]` 跨语言不对齐 (key 拼写, value 类型
  不固定); frozen dataclass + JSON 序列化能跟其他语言 schema 一一对应
- **设计**: 每个 event_kind 一个 frozen dataclass, 序列化走 `dataclasses.asdict`
  + JSON, 反序列化走 constructor
- **收益**: type-checked, mypy strict 通过; 跨语言 schema 跟 dataclass
  field 一一对应
- **误用防护**: 不允许 `dict[str, Any]` payload, 不允许 `Optional[Any]`,
  不允许 dataclass 嵌套 dict

### 4.3 候选: 弃用 — 通用事件总线 (event bus)

- **理由**: PLANNING §M6.5.7 明确不做 "通用事件总线" 抽象。event bus 隐藏
  投递语义, 跨语言 schema 无法稳定。envelope 是**专用**契约, 不复用
  到其他场景

### 4.4 候选: 弃用 — 单一 capture_time 字段

- **理由**: server-authoritative 与 本地 UTC 互相矛盾, 跨语言无法解释。
  两个字段分开是 V1 必须约束, 不是设计偏好

## 5. V1 schema 冻结内容 (摘要)

完整 schema 见 `docs/protocols/AGENT_REPORTING_PROTOCOL.md`. 摘要:

### 5.1 envelope (8 字段, 全部必填)

```json
{
  "protocol_version": "atlas-richie.reporting/v1",
  "event_kind": "RULE_SOURCE_ACTIVATED",
  "event_payload": { ... per-kind frozen dataclass ... },
  "instance_id": "uuid-string",
  "startup_epoch": 0,
  "sequence": 1,
  "captured_at": "2026-09-13T10:00:00.123456Z",
  "received_at": "2026-09-13T10:00:00.456789Z"
}
```

### 5.2 event_kind V1 枚举 (6 个, 冻结)

| event_kind | 类别 | 用途 | payload schema |
| --- | --- | --- | --- |
| `RULE_SOURCE_ACTIVATED` | source-switch | 切源 / 启源 | `RuleSourceActivatedPayload` |
| `RULE_SOURCE_STALE` | health | 不切源但状态变 stale | `RuleSourceHealthPayload` |
| `RULE_SOURCE_DEGRADED` | health | health 进一步恶化 (degraded / disconnected) | `RuleSourceHealthPayload` |
| `RULE_APPLIED` | biz-exec | 规则被成功 apply | `RuleExecPayload` |
| `RULE_BLOCKED` | biz-exec | 规则 block 一次请求 | `RuleExecPayload` |
| `RULE_FAILED` | biz-exec | 规则应用失败 (codec / type) | `RuleExecPayload` |

**禁止子任务 (M6.5.1 / M6.5.2 / M6.5.3 / M6.5.6) 在 M6.5.7 签字后直接向
V1 枚举塞项**。新增枚举值必须走 V2+ 独立 ADR。

### 5.3 health event 与 source-switch event 不混用

- 切源 → `RULE_SOURCE_ACTIVATED` (新 source_id + version 进入)
- 不切源但状态变 → `RULE_SOURCE_STALE` / `_DEGRADED` (同一 source_id
  + version, 只改 health 字段)

### 5.4 V1 兼容性矩阵

| 变更类型 | 是否破坏 V1 | 路径 |
| --- | --- | --- |
| 加 optional field | 否 | 同 major, ADR 签字 |
| 加新 event_kind | 否 (V1 枚举仍有效) | V1.1 minor, ADR 签字 |
| 改 event_kind 字符串值 | **是** | V2 major bump |
| 改 event_payload 字段语义 | **是** | V2 major bump |
| 删字段 | **是** | V2 major bump |
| 改时间字段语义 (captured_at / received_at) | **是** | V2 major bump |
| 改 protocol_version 字符串 | **是** | V2 major bump |

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| V1 冻结后, 新需求要新 event_kind 走 V2 ADR (慢) | 1.x 末新功能上线慢 | V1.1 minor 允许加 optional field; 加新 event_kind 走 minor 路径; V2 仅在破坏 V1 兼容时走 |
| `captured_at` 与 `received_at` 跨语言时区序列化不一致 | 跨语言互操作混乱 | captured_at 强制 ISO 8601 UTC with microseconds (`2026-09-13T10:00:00.123456Z`); received_at 同; 跨语言都用 `strftime("%Y-%m-%dT%H:%M:%S.%fZ")` |
| 6 个 V1 event_kind 不够用, 1.x 末需新增 | 阻塞 1.x 末功能 | V1.1 minor 允许加 event_kind, 不破坏 V1; 兼容性矩阵明确 |
| M6.5.1 / M6.5.3 / M6.5.4 implementation 偏离 envelope spec | 跨语言 SDK 不互操作 | M6.5.1 / M6.5.3 / M6.5.4 实施前必须 sign-off envelope 冻结 (本设计 doc) |
