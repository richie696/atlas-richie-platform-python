# 编码前的自省清单

> 目的：在写第一行代码**之前**判���这次实现是否会在未来引发「改一个 BUG、出 N 个新 BUG」。
> 配套的是 `REACT_ENGINEERING_STANDARD.md` 与 `REACT_CODING_STANDARD.md`，本文不替代它们，
> 只把它们变成可执行的前置检查。

## 为什么不用行数当判据

规范**明确拒绝**按行数拆分：

> `REACT_CODING_STANDARD.md:21`「拆分条件是出现独立变化原因、生命周期、协议边界或第二个
> 真实消费者，**不是超过某个行数**。」
> `REACT_ENGINEERING_STANDARD.md:15`「**不要凭行数机械拆分**」

所以「文件不超过 N 行、方法不超过 M 行」不是本工程的判据 —— 它不存在。真正的判据是
**变化原因的数量**。行数只是症状：一个 300 行的文件如果只服务一个变化原因，它是对的；
一个 120 行的文件如果同时是路由表、协议定义和状态机，它已经错了。

判据换成变化原因后，阈值反而更严：行数超限还可能只是「该拆了」，
而**两个变化原因共处一个文件就是当下的设计错误**，不管它多短。

## 自省五问

### 1. 这是面向对象代码吗？

**先答，再审。** 本工程是**函数优先**：UI 用函数组件与 Hooks，对象只用于封装
**稳定的协议、状态机、资源生命周期和可替换适配器**（`ARCHITECTURE.md`）。

因此 SOLID 在这里落在**模块职责**与**契约**上，不是类继承上。给 React 组件建基类、
用继承表达「不同页面」都是错的改造方向。

- 判据：新增能力是「加一个模块」还是「改一个已有模块的分支」？
- 是后者 → 见第 3 问（OCP）。

### 2. 每个文件/模块是否只有一个主要变化原因？

逐个候选文件回答：「什么需求变化会让我改这个文件？」

- 答出 **2 个以上** → SRP 违规，先拆。
- 判据参考：`REACT_ENGINEERING_STANDARD.md:15`「一个模块、文件或对象只承担一个主要变化
  原因；相同业务规则保持唯一事实来源」。

**当前已知的混装点**（改造中，勿再往里加）：

| 文件 | 混杂的变化原因 | 目标 |
| --- | --- | --- |
| `src/styles.css` | 主题 token / 组件皮肤 / 6 个 feature 布局 / 3 个响应式断点 | `core/styles/` + 各组件 `*.module.scss` |
| `src/ruleI18n.ts` | shell / 规则工作台 / 实时 / 总览 / 6 个 feature 文案 | `core/i18n/`（shell 域）+ `features/*/i18n/` |

### 3. 加新东西要不要改旧代码？

- 要改旧代码里的分支/条件 → **OCP 违规**。
- 正确形态：新能力 = 新模块；旧模块只在**接缝处**扩展一次。
- 典型反例：把 `if (granted.includes('rules:write'))` 写进 6 个页面 —— 加第三种能力
  就要改 6 个文件，漏一处即权限泄漏。正确形态是单一纯函数 `can(session, action)`，
  页面只提问、不判定。
- 判据参考：`REACT_CODING_STANDARD.md` §3 状态归属、§5 权限。

### 4. 同一事实有第二份拷贝吗？

有第二份就迟早漂移。凡是「必须手工保持同步」的字段对，都是定时炸弹：

- 判据参考：`REACT_CODING_STANDARD.md:21`「重复业务规则合并到唯一归属」。
- 已修：`identity` 的账号列表曾是两份 `useState`，改一处另一处看不到。
- 已修：`useRuleWorkbench` 的 `selectedId` / `draft` / `editing` 编码同一概念。
  待收敛为「选中项派生 + 草稿随选中」。

### 5. 这次改动会被现有门禁证明吗？

| 门禁 | 能证明什么 | 抓不到什么 |
| --- | --- | --- |
| `typecheck` | 类型契约、导入路径、拼写 | 运行时逻辑、Hook 依赖、stale closure |
| `build` | 能打包 | 行为正确 |
| `test:sites` | Sites 交接契约 | 页面渲染 |
| 视觉基线（DOM + 像素） | 渲染输出未变 | **交互态**、Hook 时序、effect 少依赖 |

**没有 Hooks lint 之前，不要重构带 effect 的状态机** —— 上表最后一列就是原因。
这是引入 lint 的唯一理由：它不产出功能，是给后续重构装护栏。

## 执行顺序

1. 答完五问，把结论写进本次改动说明。
2. 逐条对照上表核对，全部通过才动代码。
3. 改完跑全部门禁 + 视觉基线；有意的渲染变化必须用 `ACCEPT_RENDER` 显式声明。
4. 发现的既有缺陷单独记录，不混在本次改动里「顺手修」。

## 什么时候不适用

一次性脚本、纯数据 fixture、生成物不适用第 2–4 问 —— 它们没有跨页面复用面。
但第 5 问始终适用：它们仍然要过 `typecheck` 与视觉基线。
