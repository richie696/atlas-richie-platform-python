# T05 Observation API closure — focused test design

## Frozen decisions

- **Approved 2026-10-15:** T05.1 uses authenticated Metrics V2 Reporter enrollment and accepted durable snapshots as its only runtime identity/heartbeat/metric authority. Every worker is a separate Dashboard instance; its `instanceId` is unique in Reporter enrollment. A reporter without an accepted snapshot is not listed; a revoked reporter is excluded; a reporter whose latest receipt is older than three Metrics V2 cadence intervals remains visible as stale. The directory exposes PROCESS scope only. HOST/CONTAINER identities and rule receipts remain unknown.
- **Approved 2026-10-15:** T05.2 uses an independent versioned Incident Event protocol: Runtime produces events and Collector persistence is the durable source for the incident timeline. Protocol compatibility is based only on authenticated Runtime↔Collector negotiation; absence is `unknown`, never inferred from configuration, package versions, or code constants. Negotiation facts are per enrolled worker, not one lossy global value.
- **Approved 2026-10-15:** Incident trigger policy belongs to the consuming application, not the Sentinel library. The application decides whether a fault qualifies, selects its typed fact/threshold/severity, and explicitly invokes the producer. Sentinel must not add an automatic `IncidentPolicy`, infer incidents from arbitrary Metrics V2 samples or ordinary rejections, or claim that a generic producer package supplies application policy.
- Existing Agent Reporting V1 and Metrics V2 wire contracts remain unchanged. Publication-related incident facts remain unavailable until T03.3 provides authenticated publication receipts.

The final T07.1 gate still must exercise a consuming application explicitly invoking the Runtime-facing producer, Reporter through Collector persistence, and browser-visible timeline/system protocol APIs. ## Runtime Incident Producer V1 — implementation candidate

- The consuming application owns the decision and calls the Sentinel Runtime-facing `IncidentEventProducer` only after its explicit incident policy has classified a fault. The producer creates a typed `IncidentEventV1` from the caller-selected fact, threshold, and severity. It is bound to the current process epoch (normally shared from the Metrics V2 Reporter at explicit application assembly), and supplies event ID and UTC occurrence time. It does not sample metrics, hard-code thresholds, or promote an ordinary metric sample to an incident.
- The optional reporting extension exposes `report(event) -> durable receipt`. The immutable event can be retained and retried with its same `event_id`; the reporter serializes once, uses the same exact bytes for bounded transport retries, validates the returned event ID and body digest before success, propagates cancellation, and exposes only stable redacted transport/receipt errors. No hidden queue/background worker is proposed; the owning application chooses where to await this network operation.
- The protocol-specific HTTPS/mTLS Adapter uses the existing rotating credential-provider seam and owned `atlas-richie-http` client; TLS identity is never copied into the body or logs. Runtime process epoch must match the enrollment's current epoch, and instance identity continues to be derived by Collector from the verified certificate principal.
- GoF assessment: Adapter is required to isolate HTTP/mTLS and keep transport errors/types out of the incident contract. A single reporter entry point may encapsulate the one reporting use case, but no generic Facade framework, Observer/Mediator, Strategy registry, or State hierarchy is justified. Shared mTLS mechanics should be extracted only if Metrics V2 and Incident V1 can use the same bounded transport contract without renaming/leaking metric semantics.
- Before closure, add producer tests for shared process epoch, explicit threshold/severity, UTC occurrence time, and stable event ID reuse; retain contract tests for wrong event epoch and receipt mismatch; transport tests for exact-byte retry, redacted errors, credential rotation and cleanup; and real loopback mTLS Collector acceptance proving producer→Reporter→durable ACK, exact replay, revocation and SQL read-back through the timeline authority. Direct SQL insertion or injected peer-certificate ASGI tests alone do not prove the producer path.

This document records the test design; the protocol freeze and current acceptance status are maintained in `protocols/INCIDENT_EVENT_PROTOCOL.md` and process checklist §15.1236. Product decisions above are approved. The authenticated hello/accept exchange, durable per-worker SQL fact, versioned read route, React query and display are implemented; the typed Runtime producer has been exercised through real loopback mTLS Collector acceptance for SQLite, PostgreSQL, and MySQL (process checklist §15.1205). The project owner approved the consolidated protocol/security/persistence review on 2026-10-15. A disposable Docker Desktop Kubernetes namespace then ran the CronJob controller and actual retention CLI against seeded SQLite data; expired data was deleted, live data preserved, and all temporary namespace/PVC/image resources were removed (§15.1236). This closes T05.2's authorized isolated-equivalent functional acceptance, not production/multi-node topology (T00.3). A production trigger policy is intentionally owned by each consuming application and is not a Sentinel-library closure item; T07.1 must exercise an explicit consumer call. Final T07.1 browser E2E remains open. Go/Java shared-fixture conformance is supporting evidence, not production SDK evidence or a substitute for the recorded owner approval.

## Independent Incident Event negotiation closure and remaining acceptance

- **Approved product semantics:** Incident Event is its own versioned Runtime→Collector protocol; the Collector persists accepted typed events; compatibility must come from the authenticated negotiation for the exact protocol, and no observation is `unknown`.
- **Implemented slice:** `POST /api/reporting/v1/protocol-negotiations/incident-events` accepts an exact protocol-version hello only over enrolled mTLS, stores the independent Incident Event fact before returning, and reports `compatible`/`incompatible`. `GET /api/v2/system/protocol-observations/incident-events` is session-protected, paginated, worker-scoped, revocation-aware, and does not expose certificate principals. React renders a distinct Incident Event worker list; no handshake remains `unknown`. Existing Console API 0.5.0 routes/DTOs, Agent Reporting V1, Metrics V2, and incident ingest/ACK semantics remain unchanged.
- **Verified:** unit/store and Console OpenAPI/API parity checks; real loopback mTLS writes for two distinct workers; same worker's Agent Reporting and Incident Event facts remain independent; unsupported version and revocation behavior; durable SQL rows with SQLite, PostgreSQL, and MySQL; frontend HTTP boundary validation and three-locale mounted panel rendering. See process checklist §15.1199.
- **T05.2 closure:** protocol freeze and the authorized isolated-equivalent scheduled retention acceptance are complete (§15.1236). This does not assert target-cluster production deployment, multi-node storage, Ingress/TLS, or production Secret delivery; those remain in T00.3. Trigger policy is explicitly outside the Sentinel library; the final T07.1 test driver must act as a consuming application and invoke the typed producer explicitly. Full product journey remains separately gated by T07.1.

## Protocol observation cardinality gap

- The user-confirmed deployment unit is one enrolled worker per Dashboard instance. An authenticated Runtime↔Collector negotiation is therefore instance-scoped, and two workers may legitimately negotiate different protocol versions during a rolling upgrade.
- The frozen Console API 0.5.0 `GET /api/v1/system/protocols` contract permits at most one item per protocol boundary (`kind` is unique; `active` is a single nullable version and compatibility is a single enum). It cannot losslessly represent a mixed-version worker fleet or identify which worker produced a negotiation fact.
- The approved product model makes every worker a separate Dashboard instance, so the read model must preserve per-worker observations. Do not select the newest/last negotiation as deployment-wide `active`, collapse observed disagreement to `unknown`, or widen the frozen API in place. Implement an additive, separately versioned Console contract for bounded instance-level observations and retain the existing 0.5.0 endpoint unchanged.
- Focused tests must include two enrolled workers with the same version, two workers with different versions, one stale/revoked worker, and no observed handshake. The read model must preserve or explicitly aggregate each case according to the newly approved contract; a single-worker happy path is insufficient.

## Protocol fact-source scope gap

- The current system page defines three product boundaries: `rule-config`, `agent-reporting`, and `cluster-token`. A Runtime↔Collector handshake can authoritatively establish only the boundary actually negotiated with that Collector. It cannot attest which rule-source format a worker loaded from Nacos/Consul or which protocol a separate Token Server negotiated.
- Until each boundary has a matching authenticated observation source, those other rows must remain `unknown` (or be omitted as partial observations); Collector-selected values must not be projected onto them. `supported` capability metadata and `active` deployment facts remain separate.
- Contract review must bind every observation to `(instance, boundary, peer/authority, selected version, observed time)` and specify freshness/revocation behavior. Required negative tests prove a valid Collector handshake cannot make `rule-config` or `cluster-token` appear compatible.
- Keep all three product boundaries visible with boundary-specific authority. Runtime↔Collector negotiation may populate only `agent-reporting`; `rule-config` and `cluster-token` remain `unknown` until their Nacos/Consul and Token Server authorities respectively provide authenticated facts. `supported` capability metadata is not an active negotiation result.
