# T03.4 React-to-Python Rule Catalog HTTP Integration

## Purpose

Close one evidence gap between the formal React rule-catalog HTTP adapter and
the Python Console's authenticated route without running the final browser E2E
or contacting a real configuration center or database.

## Risk-to-test matrix

| ID | Risk / source | Layer | Preconditions and action | Assertions | Cleanup / boundary |
|---|---|---|---|---|---|
| T03.4-HTTP-01 | UI-R01 / Console bootstrap, CSRF refresh, and `createRuleSetHttp` catalog read | Cross-process HTTP integration | Start an ephemeral loopback Python ASGI Console with synthetic session/projection ports; the production React identity adapter reads bootstrap and receives CSRF, then the rule adapter refreshes and reads over `fetch` | Bootstrap initializes; the refresh POST passes the real Origin/double-submit CSRF route; query scope survives the wire; a non-empty rule, source label, checksum, revision, and freshness are decoded by the formal adapter | Stop only the child process created by this test; no DB/provider mutation. This is not browser E2E or a live Nacos/Consul acceptance. |
| T03.4-HTTP-02 | Session-protected catalog read | Cross-process HTTP negative case | Invoke the same formal rule adapter without the session cookie | The Python route rejects the request as unauthenticated; no rule facts are returned | Same cleanup as above. |
| T03.4-UI-01 | UI-R01 / mounted production Rules page backed by Python HTTP | Mounted UI + cross-process HTTP integration | Start the same synthetic Python Console, bootstrap the production transport, then mount `RuleConsoleContainer` with the production `createRuleSetHttp` adapter | The page itself issues the refresh and catalog GET; the returned resource, threshold, source label, and response freshness render in the catalog | Stop only the ASGI child and dispose the React/Vite/transport owners. Scope and non-catalog binding ports are synthetic; not live provider/SQL or browser E2E evidence. |
| T03.4-LIVE-01 | AC-R01 / actual registered provider data rendered by the production Rules page | Real-provider integration + SQL projection + ASGI HTTP + mounted UI | For each provider, start the existing exact-owner acceptance fixture, seed one randomized provider rule target and SQL binding, externally update its rule value, then start the actual `build_app()` over loopback and mount the production page via the same Python runner | No Runtime or business request is needed; the current resource/source/value from provider→SQL→Console HTTP→React are visible, the refreshed provider revision/checksum changes, and secret material is absent | Consul uses only the wrapper-created loopback service and deletes its exact KV key. Nacos uses only its exact disposable fixture/container and temporary trust material. Dispose the in-memory SQL engine, ASGI server, React/Vite/transport, and provider fixture. This is not browser E2E. |

## Run

From `components/sentinel/dashboard-prototype`:

```sh
npm run test:integration:rule-catalog
```

The HTTP/UI tests use the repository's Python `uv` project and existing Node
test/Vite infrastructure. Their session cookie, binding scope, and catalog
projection data are synthetic; bootstrap/CSRF, refresh, and catalog HTTP
routes are production composition. The mounted test drives the actual React
Rules page through its production catalog HTTP adapter.

The live provider tests reuse the existing scoped Consul and disposable
authenticated Nacos acceptance fixtures and call
`verify_mounted_rule_catalog_page()` after a real provider update. They render
the production Rules page from that provider-backed SQL projection through the
real Python HTTP route. They do not use a user-owned database, do not start a
Runtime, and are not the final T07.1 browser E2E.
