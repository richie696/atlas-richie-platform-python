# B0.3 标准部署多规则源 provider 装配验收

## 目标与边界

标准 `sentinel-console serve` 部署可显式同时处理 Nacos 与 Consul 发布工作；仍由每条冻结 target 的 `provider` 选择准确 adapter。provider 未显式启用、缺少该 provider 网络 grant、网络策略与 provider 不匹配时必须 fail closed。Nacos 与 Consul 共享当前部署选定的 Sentinel rule profile；不同 profile 编码仍不在本切片范围内。

此变更复用既有 `RulePublicationProviderRouter`、provider adapter、SQL outbox provider filtering、网络 target policy、TLS 与 credential resolver；不新增业务规则、协议字段、自动发现或隐式 Secret/KMS。单 provider 环境变量保持兼容；新复数配置与旧单数配置同时出现时拒绝启动。

### Correction: MySQL publication timestamp precision (2026-10-13)

The preceding entry's clock diagnosis was incomplete: `_millisecond_instant` and both production composition clocks already supplied UTC millisecond instants. A later rerun against MySQL exposed the actual remaining defect: the four `console_rule_publication` timestamp columns still used default second-precision `DATETIME`, unlike the worker's millisecond contract. A live MySQL 8.4.11 probe confirmed `03:12:36.900000` is rounded to `03:12:37` by plain `DATETIME`, while `DATETIME(3)` preserves `03:12:36.900000`; the stored phase observation can therefore appear later than completion and leave a successfully published operation pending. Migration `0022_millisecond_publication_times` upgrades those columns to `DATETIME(3)`; ORM metadata now matches. This supersedes the earlier statement that worker clock precision alone explained the MySQL symptom.

- **Verification:** migration precision and MySQL rounding probes on MySQL 8.4.11 **1 passed**; installed CLI + MySQL/Consul/Nacos dual-provider workflow **1 passed in 29.90s**; PostgreSQL 16 parity rerun **1 passed in 21.74s**; focused worker and mutation completion tests **2 passed in 0.87s**. Both owner runners cleaned their disposable containers.
- **Boundary:** confirms the successful dual-provider path and timestamp schema precision only; fault-window coverage and React→Python browser E2E remain open. B0.3/B0.5 remain open.
