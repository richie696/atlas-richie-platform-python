## 0. 摘要 (TL;DR)

| 维度 | 结论 |
| --- | --- |
| **总体决策** | **1.x 不出 `sentinel-dashboard-aggregator` 包**; **1.x 不实施 Web UI** |
| **1.0 范围** | 不含 |
| **1.x 范围 (M5.4.1 候选)** | 推迟,需用户单独批准 + 新独立 ADR (不得复用 OpenSergo ADR-SEN-016) |
| **2.0 路径** | 待 2.0 触发条件出现 (M5.4.1 评估 + 用户批准 + DESIGN.md §3.1 修订) 后评估 |
| **用户感知** | 当前用户可用现有 `SentinelEngine` metrics hook / 业务 OTel 集成 自建 dashboard; 1.x 库不提供 |

**核心结论**:

1. `atlas-richie-sentinel` 主包 0 3rd-party 依赖 (DEPENDENCY_POLICY.md), Dashboard 强依赖 web 框架 (FastAPI / Starlette / Flask / ...) 和数据库 (TimescaleDB / ClickHouse / Prometheus), 任何 1.x 集成都会破坏主包 0 依赖约束。
2. 主包仅暴露 `MetricRegistry` (M1.4) / Reporter wire 协议 (M6.5), 任何"完整 dashboard"必然涉及"抓取 → 存储 → 渲染"全栈, 不属于 library 范畴。
3. M6.5 父协议 V1 已在 2026-09-13 5-owner 签收 Frozen, Collector 是 Java/Go 服务端独立仓, 1.x 范围不含 Python Collector / Dashboard.
4. PLANNING §M6.6 已明确"默认无 Deliverable" + "推迟到 1.x" + "需用户单独批准", 与本评估一致。

## 1. 范围与不在范围

### 1.1 评估范围

- 聚合 Dashboard / Web UI 在 1.x 阶段的可行性、必要性、依赖冲突与替代路径。
- 是否需要 `sentinel-dashboard-aggregator` 新发行包。
- 是否复用 OpenSergo Dashboard (外部依赖)。
- 与 M6.5 Reporter 协议的关系 (Collector 是 Java/Go 仓, Python 主包不需要再实现 Collector)。
- 用户替代路径: 业务 OTel / Prometheus 集成 / 自建 dashboard.

### 1.2 明确不在范围 (Non-Goals)

- **不实施** 任何 1.x 阶段 `sentinel-dashboard-aggregator` 仓。
- **不引入** Web 框架 (FastAPI / Starlette / Flask / Django) 到主包或 1.x 任何 extension.
- **不引入** 数据库驱动 (psycopg / sqlalchemy / asyncpg) 到主包或 1.x 任何 extension.
- **不引入** TimescaleDB / ClickHouse / Prometheus 客户端到主包或 1.x 任何 extension.
- **不修改** DESIGN.md §3.1 发行包表 (1.x 阶段不加新行)。
- **不评估** Grafana / OpenSergo Dashboard / Datadog 等外部产品的集成 (留给用户按需自建)。

## 2. 关键决策

### 2.1 不出 `sentinel-dashboard-aggregator` 包

**理由**:
- 主包 0 3rd-party 依赖 (DEPENDENCY_POLICY.md §3); 任何 Dashboard 至少需要 (1) HTTP 服务端 (2) 模板引擎 (3) 存储后端 (4) 图表渲染, 任意 1 个都会破坏 0 依赖约束。
- 1.x 原则 "library 不替用户做 dashboard" (R-219 阶段设计治理: 用户明确反对 "framework 替用户做 view layer")。
- 已有 `MetricRegistry` (M1.4) 暴露 `Snapshot.statistics()` / `Snapshot.window()`, 用户可直接接 OTel / Prometheus 客户端。

**不实施 (1.x)**:
- 1.x 阶段不发 `atlas-richie-sentinel-dashboard-aggregator` wheel。
- DESIGN.md §3.1 发行包表不加新行。
- ADR-SEN-018 (M6.7 评估同步记录) 不升 Accepted.

### 2.2 Collector Python 实施不在 1.x 范围

**理由**:
- M6.5.4 明确: "1.0 范围**不**含 Collector Python 实现 (Collector 是 Java/Go 服务端独立仓, V1 协议只冻结 wire contract)".
- 跨语言 hello world web 服务 (commit `6cf2f33`) 已验证 wire contract 互操作, Go + Java 各 13 单测全过。
- 完整 1:1 镜像 codec 留 1.0 publish 前 worker 后台跑。

**不实施 (1.x)**:
- 1.x 阶段不发 `atlas-richie-sentinel-collector` Python wheel.
- Collector 服务端由 Java/Go 仓独立维护, 1.x 库只冻结 wire 协议 (`docs/protocol/reporting-protocol-01/02-envelope/transport-v1.md`).

### 2.3 推迟到 1.x (M5.4.1 候选) 的条件

按 PLANNING §M6.6 + DESIGN §25 决策记录约束, 任何后续阶段纳入 Dashboard 需要同时满足:

1. **用户显式批准**: 1.x 阶段需要新独立 ADR, **不得复用 OpenSergo ADR-SEN-016** (DESIGN §25 决策)。
2. **ADR-SEN-018 升 Accepted**: M6.7 WSGI/sync 评估同步记录, 当前是 Proposed, 用户签字才可触发后续。
3. **DESIGN.md §3.1 修订**: 发行包表加新行 (例如 `atlas-richie-sentinel-dashboard-aggregator`), 含依赖列表 (FastAPI / SQLAlchemy / 模板引擎 / ...) + 主包契约 (MetricRegistry / Reporter wire).
4. **DEPENDENCY_POLICY.md 修订**: 0 3rd-party 约束仅限主包; extension wheel 允许 3rd-party 依赖, 但需逐个 ADR 签字。
5. **M5.4.1 评估触发**: 用户业务场景出现 dashboard 强需求 (监控多服务聚合 / 长期历史查询 / 告警).

## 3. 用户替代路径 (1.x 已可用)

1. **MetricRegistry 接入 OTel**: `atlas_richie.sentinel.engine.MetricRegistry.snapshot()` (M1.4 已实施) 输出 `Snapshot` (规则统计 / 滑动窗口 / 系统指标), 用户用业务 OTel SDK 包装后导出。
2. **Reporter wire 协议接入 Prometheus**: Collector (Java/Go) 端用 wire protocol 收 envelopes 后转 Prometheus exposition format; Python 业务无需任何代码改动。
3. **业务自建**: 用户用任何 web 框架 (FastAPI / Django) + 数据库 (TimescaleDB / ClickHouse) 自建 dashboard; Python 库只暴露 1.x 公共 API.
4. **Grafana 模板**: 用户可基于 `MetricRegistry` 输出写 Grafana dashboard JSON, library 不内置。
