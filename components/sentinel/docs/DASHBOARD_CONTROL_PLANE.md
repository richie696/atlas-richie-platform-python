# Sentinel Dashboard：规则控制台与运行观测设计

> 状态：产品方向已确认；六页交互设计原型已实现。接口、指标采集、Nacos/Consul 回写与生产 UI 尚未实现或冻结。
> 日期：2026-09-14。
> 范围：独立管理控制台，以及现有 per-process Dashboard 的观测页面演进。
> 本文不改变 M6.6 已有 per-process Dashboard 的交付状态，也不把独立控制台算作已完成。

## 1. 产品边界与用户任务

Sentinel 运行时只消费规则、执行准入和暴露本进程状态。**配置中心是线上规则的唯一事实来源**：每个「应用 × 环境 × 规则集」明确绑定一个生效的 Nacos 配置项或 Consul KV key，不把业务数据库或进程内存当作规则源。用户在控制台编辑规则时，写入选定配置中心；运行时从该配置项重新读取并校验完整快照。

现有 `atlas-richie-sentinel-dashboard` 是随 Engine 部署的 per-process 诊断页面，保留本进程的状态、规则和指标查看能力；它不持有配置中心写凭证，也不声称看到全应用或全主机状态。独立部署的管理控制台负责配置中心回写、版本与冲突处理、跨实例生效观察、统一运维页面。两个界面可以共享视觉语言，但必须明确标出当前观察范围。

首要用户任务：

1. 选定应用、环境和规则集，知道当前配置中心版本及运行实例实际加载的版本。
2. 在一页内看清资源压力、吞吐、延迟和规则阻断趋势，并下钻到实例或资源。
3. 借助场景化表单创建或修改规则，验证、预览差异、写回配置中心并跟踪生效。
4. 遇到异常时把历史规则作为**新版本**重新发布，继续观察生效结果。

不做租户、组织树、数据范围授权、多级审批或内置 TSDB/告警产品。控制台也不替代 Nacos/Consul 自身的存储和运维。管理侧未来若要持久化跨会话草稿、审批或完整审计，其存储与线上规则事实来源严格分开；未选定可靠存储前不承诺这些能力。

## 2. 最小权限模型

控制台只要求内部用户经过统一登录/网关认证，不自建一套身份系统。服务端仅判断两个能力：

| 能力 | 允许的页面和动作 |
| --- | --- |
| `metrics:view` | 总览中的流量/资源指标、趋势图、实例指标详情和指标查询 API。 |
| `rules:write` | 新建、修改、停用、发布、回滚规则；发布和回滚都必须记录操作者及结果。 |

登录用户可查看规则摘要、版本和规则源健康状态；没有 `metrics:view` 时不请求或渲染图表数据，不能以空图或 0 值伪装无流量。没有 `rules:write` 时页面只读，深链和 API 仍由服务端拒绝写操作。两项能力可以独立授予，也可以同时授予；首版不增加 Viewer/Editor/Approver 等角色层级。连接地址及写凭证由部署配置管理，不提供普通用户可修改的连接设置页面，因此不需要第三种页面权限。

简化权限不等于放弃安全：配置中心写凭证只在管理服务端；写入必须有目标环境确认、鉴权、审计、CSRF 防护（使用浏览器 Cookie 会话时）、敏感字段脱敏与失败反馈。现有 per-process Bearer admin token 与统一控制台的登录授权是两套边界，不相互冒充。

## 3. 指标口径、采集来源与缺口

### 3.1 先标明观察范围

每条曲线必须带 `scope`（host/container/process/instance/application）、`source`、采样时间、单位、聚合窗口和数据新鲜度。一个 worker 的数字不能标成「应用总量」；进程 CPU/RSS 不能标成「服务器 CPU/内存」；Kubernetes 容器压力不能与宿主机压力混为一谈。跨实例汇总只合并同口径、同窗口且可识别实例身份的数据，并显示已上报实例数与未知实例数。

| 区域 | 首要指标 | 数据来源与约束 |
| --- | --- | --- |
| 服务器/容器压力 | CPU 使用率、内存已用/限制、负载；可选磁盘、网络 | Host/容器采集器或现有可查询的监控后端。当前 Engine 的默认 `SystemMetricSampler` 只提供部分 load，CPU usage 可为 `None`，不能凭它宣称完整主机监控。 |
| Python 进程压力 | CPU、RSS、in-flight、event-loop lag；可选 GC | 显式启用的进程/ASGI 采样器。没有采样器时显示「未接入」，不显示 0。 |
| 流量 | HTTP QPS、资源调用率、准入/拒绝率、错误率 | HTTP QPS = 入站 HTTP 请求数在选定窗口的增量/秒；资源调用率 = Sentinel entry 增量/秒，二者不能混称。计数器重启或溢出须分段处理。 |
| 业务吞吐 | TPS | TPS = 完成的**业务事务**数/秒，必须由应用明确标记事务边界与成功口径。未接入业务事务埋点时隐藏 TPS，不从 HTTP QPS 或 `succeeded` entry 猜测。 |
| 响应时间 | 平均 RT、p50/p95/p99、样本量 | 同一时间窗内的完成请求耗时；p95/p99 需要可聚合的 histogram/桶，不能用各实例百分位或累计平均值再求平均。 |
| Sentinel 保护 | 阻断率、阻断原因、熔断状态、规则版本漂移 | 来自受控低基数指标与规则源/实例回执；没有完整上报链路时只展示本进程已知事实。 |

当前 `MetricRegistry` 提供累计 `admitted/blocked/succeeded/failed/cancelled` 和累计 `avg_rt_ns` 快照，per-process 页面每 5 秒通过 SSE 发送快照。它**不直接提供**可靠的区间 QPS、区间 RT、p95/p99、TPS 或完整主机压力。图表实现前须补齐：可单调处理的计数器、RT `sum/count` 与 histogram、时间序列采集/查询、重启 epoch、丢点与采样质量状态；这些改动不能通过在浏览器端对累计平均值做差来规避。跨进程历史图优先查询已有指标后端，Sentinel 主包不内置 TSDB。

近实时视图建议提供 5/15 秒级刷新与 15 分钟、1 小时、6 小时、24 小时范围切换；具体采样间隔和保留期由后端能力决定，不在 UI 中假定固定 SLA。每幅图标注发布版本切换时间；延迟、断线、无权限、无样本和采样器未安装是不同的空状态。

### 3.2 图表交互

- 顶部固定「应用 / 环境 / 观察范围 / 时间范围」，切换后 URL 保留上下文；默认展示当前范围的新鲜度。
- 第一屏四个摘要：服务器/容器压力、QPS、RT p95、规则阻断率；每张卡同时给出单位、时间窗、同比/环比所依赖的真实数据，数据不足时不画趋势箭头。
- 下方两排趋势：资源压力（CPU、内存、load）与业务表现（QPS/TPS、RT、错误/阻断）；图上的发布标记可跳到规则差异和实例生效情况。
- 支持按实例、资源、规则、阻断原因下钻；跨实例汇总展示覆盖率。多个折线的单位不同则分图或双轴明确标注，不把 QPS 和 RT 放在同一无标签刻度。
- 颜色以状态为辅，配合文字、图例和图形；键盘可切换时间范围及查看数据表，图表提供可访问的表格替代视图。

## 4. 六页信息架构与交互合同

视觉基线以「实例健康矩阵 + 所选实例右侧诊断」为应用页核心；总览采用全局流量、防护趋势和应用排行的大盘结构。两个页面共用深色状态色、规则发布时点标注、紧凑表格与应用/环境/时间上下文。其余四页沿用同一设计语言，但以各自运维任务为中心，不复制一屏相同 KPI。

| 导航 | 必须回答的问题 | 首屏必备内容 | 主要操作与下钻 |
| --- | --- | --- | --- |
| **总览** | 哪些应用异常，流量变化是否与保护行为同步？ | 异常摘要、Nacos/Consul 与规则覆盖状态、同时间轴 QPS/阻断率、应用状态表 | 点击异常应用或表行进入「应用与实例」；切换时间窗须重算图表，不能只改标签。 |
| **应用与实例** | 异常在何实例、何层级，压力与 QPS/拦截是否同步？ | 按宿主机分组的实例矩阵；所选实例容器/进程/宿主机 scope、CPU/内存、QPS/拦截双轴图、规则版本 | 筛异常、选实例、切 scope、跳规则；没有某层采样时明确「未接入」，不能重复展示容器数。 |
| **规则** | 当前哪条规则来自何处、影响什么资源、拟变更与当前版本有何差异？ | 可按应用/类型/资源搜索的规则清单；五类 Sentinel 兼容规则的专用字段、基准版本、作用范围与完整 JSON 数组预览 | 场景化表单→校验→差异→发布确认→配置中心写入/回读→实例生效；不同规则类型各有专用字段，不能用通用数字阈值代替。 |
| **实时监控** | 最近 15 分钟/1 小时流量、RT、阻断和 CPU 如何联动？ | QPS、RT p95、阻断率和 CPU 卡片；同时间窗四组曲线，规则发布时点 | 按指标/资源/应用筛选、暂停/继续自动刷新、跳故障；未接入实时后端时只允许有明确标签的静态样本回放。 |
| **故障分析** | 先发生了什么，证据支持哪种下一步？ | 严重/警告计数、按时间倒序的资源/RT/规则变更事件、所选事件证据和建议动作 | 按应用/级别/时间筛选、选择事件、跳实例/版本差异；时间相关不直接断言因果。 |
| **系统管理** | 配置中心、采集、上报和授权链路是否健康？ | Nacos/Consul 只读连通性与能力、采样覆盖、实例回执覆盖、Collector 状态 | 连接与采集 / 权限与审计 / 协议与版本三分区；连接凭证仍走部署配置，不在普通控制台修改。 |

### 4.1 全局作用域和状态约束

- 顶部导航固定上述六项，保留可分享的页面/筛选上下文。桌面总览优先把异常、趋势和应用表放进首屏；应用页以矩阵为主，详情随选中实例切换。窄屏按「摘要→矩阵→详情」单栏排列，宽表可横向滚动，但第一列身份保持可辨。
- 应用筛选必须改变对应应用的数据；没有该应用的实例级数据时显示缺口，不能用另一应用的行填充。跨应用大盘的应用选择可以直接下钻，不应让全局曲线假装变成应用曲线。
- 时间范围只提供后端真实可查询的窗口；窗口外的发布时点不画标记。查询失败、迟到、缺样、无权限和 0 值分别呈现。
- 总览、实时监控与故障分析的关键卡片至少展示值、单位、scope、窗口、来源和新鲜度；没有 histogram 就不画 p95。实例页的 QPS 与阻断率必须双轴标注，避免共用一套无单位刻度。
- 所有规则操作区分「本地草稿已验证」「配置中心写入成功」「回读一致」「实例已生效」。前一个状态绝不能被 UI 文案合并为后一个状态。

### 4.2 数据与权限接入表

| 页面 | 读模型 / 最小后端能力 | 写能力 |
| --- | --- | --- |
| 总览 | 应用目录、实例覆盖数、时序聚合、规则源健康、有效规则版本 | 无 |
| 应用与实例 | 实例目录与身份、host/container/process 分层样本、实例规则回执、按 resource 的保护指标 | 无 |
| 规则 | 配置中心权威快照、schema 解释器、来源/版本、实例回执、发布历史 | `rules:write` 经管理服务执行完整快照写入；含校验、冲突处理、审计和回读 |
| 实时监控 | 指标后端按 app/resource/instance/window 查询，质量状态与发布标记 | 无 |
| 故障分析 | Agent Reporting 事件、资源/规则发布审计、可追溯的相关指标窗口 | 无；建议动作不自动更改规则 |
| 系统管理 | 配置中心 read/health、指标后端和 Collector health、权限声明、协议版本 | 首版不提供连接凭证的网页写入 |

`metrics:view` 保护指标查询和图表；`rules:write` 保护规则写入 API。服务端以操作授权为准，界面隐藏按钮不是安全边界。规则摘要与版本可按 §2 的约定只读展示。

### 4.3 Sentinel 规则兼容格式与表单合同

控制台把 Sentinel 的五类规则作为**配置输入兼容 profile**：`FlowRule`（流量控制）、`DegradeRule`（熔断降级）、`SystemRule`（系统保护）、`AuthorityRule`（来源访问控制）和 `ParamFlowRule`（热点参数）。每个「应用 × 环境 × 规则类型」配置项的内容是一个同类型的 JSON array；规则类型由配置绑定决定，**不**向每个 rule 对象临时塞入非 Sentinel 的 `ruleType` 字段。这样 Nacos 或 Consul 中的内容可以继续被同 profile 的 Sentinel 客户端或治理工具读取。

| 类型 | 必须可编辑的兼容字段 | 条件字段与 UI 约束 |
| --- | --- | --- |
| `FlowRule` | `resource`、`limitApp`、`grade`、`count`、`strategy`、`controlBehavior`、`clusterMode` | 非直接策略必须填写 `refResource`；慢启动显示 `warmUpPeriodSec`；排队等待显示 `maxQueueingTimeMs`；开启 cluster mode 才编辑 `clusterConfig`。当前 1.0 的 Token Server 配额变更标为「保存后重启生效」。 |
| `DegradeRule` | `resource`、`grade`、`count`、`timeWindow`、`minRequestAmount`、`statIntervalMs` | 慢调用比例策略额外要求 `slowRatioThreshold` 在 `(0, 1]`；`count` 的业务含义随策略切换，表单必须同步说明单位。 |
| `SystemRule` | `highestSystemLoad`、`avgRt`、`maxThread`、`qps`、`highestCpuUsage` | 该类型没有 resource；未启用项序列化为 `-1`，至少必须启用一个阈值；CPU 用 `0..1`，不能展示为百分数后再原样写入。 |
| `AuthorityRule` | `resource`、`limitApp`、`strategy` | `limitApp` 是英文逗号分隔的 origin 列表；白名单与黑名单必须在表单中明确说明未匹配来源的结果。 |
| `ParamFlowRule` | `resource`、`grade`、`count`、`durationInSec`、`paramIdx`、`paramFlowItemList` | `paramIdx` 从 0 开始；例外项保留 `classType`、`object`、`count`。`classType` / `object` 是 Sentinel Java 格式的表达，跨语言 runtime 必须由 codec 明确校验，不能把它假定为 Python 或其他语言的通用类型系统。 |

控制台内部仍以 Atlas 的 canonical `RuleSnapshot` 处理完整快照、版本、来源和发布状态；`SentinelRuleCodec` 是管理侧的**输入/输出转换边界**，不是让 Engine 依赖 Java SDK 数据类。该 codec 必须：解析同类 JSON array、拒绝字段类型/范围/条件不一致的候选快照、在规范化后保留已支持字段的精确语义，并在目标 profile 不支持的字段上明确失败。未知字段不得被静默删除后写回配置中心；首版应阻止发布并展示字段路径，后续若需要透传必须以显式、可审计的扩展字段策略另行冻结。

表单和 JSON 预览是一份草稿的两个视图：表单改动立刻更新候选 array；「校验」只代表 schema/语义校验成功；「发布」以后还要分别显示配置中心写入、回读一致和实例实际加载。任何状态都不能跳过或合并。

#### 4.3.1 国际化与协议键边界

控制台首版语言为 `zh-CN`、`en-US`、`ja-JP`。所有对人可见的规则工作台标题、字段名称、提示、下拉选项、校验反馈和状态文案都必须来自语言资源；不得把 `resource`、`count`、`grade`、`paramIdx` 等协议键当作字段标签。字段标签应使用稳定业务术语，例如「资源名称 / Resource name / リソース名」「单机阈值 / Single-node threshold / 単一ノードしきい値」。

语言仅影响**展示**：配置中心的 JSON array、Nacos/Consul key、规则资源名、版本、枚举编码、审计事实和 canonical `RuleSnapshot` 均保持原值，不能随浏览器语言变更。原始协议键可以出现在只读 JSON 预览中，并须明确标识为配置内容。翻译缺失时回退到 `zh-CN` 并记录开发期检查项；禁止回退为协议键名。

语言包按领域拆分，规则工作台拥有自己的资源文件；其他五页在各自开发时迁入同一 locale 选择和资源机制。原型已交付规则工作台及公共导航/示例提示的三语言包；在六页所有用户可见文本完成迁移前，不得把原型宣传为「全控制台语言覆盖已完成」。语言选择属于本机界面偏好，不进入 URL、规则草稿、配置中心或审计事件。

### 4.4 交互原型与生产边界

[`dashboard-prototype`](../dashboard-prototype/) 是可运行的 React 交互设计原型，六页均使用标明的示例数据。它验证信息层级、样式、可用性和筛选/下钻动线；不请求生产 API、不读取凭证、不向 Nacos/Consul 写入，也不证明 M6.6 的 per-process Dashboard 已具备这些页面。原型已提供上述五类规则的本地草稿表单、条件字段和 Sentinel 兼容 JSON array 预览；它只做本地语义校验，不制造发布成功提示。真实 codec、完整快照合并、写回与跨进程图表仍按 §6 分阶段实施。

第一次使用只展示不超过四步的轻引导：确认配置中心连接 → 绑定应用/环境/规则集 → 观察一个真实资源 → 创建并验证第一条规则。引导不代替发布确认；熟练用户可跳过。规则表单先让用户选择「保护接口流量 / 控制并发 / 下游熔断 / 热点参数 / 调用方访问控制 / 系统保护」等场景，再渐进展示必要字段，旁边用业务语言解释触发后会发生什么；高级模式才展示全部字段和规范快照。表单、原始快照与发布预览共用一套语义校验。

布局上，桌面端用固定顶部导航与作用域、图表与规则详情的两栏工作区；窄视口改为单栏摘要和详情区，不把宽表硬缩。状态至少覆盖首次空白、无权限、采集器未接入、数据过期、配置中心离线、发布冲突、部分实例未生效和回滚失败。所有写操作保留输入与差异，失败后可安全重试但不得静默重放。

## 5. 配置中心写入与版本状态

管理服务内的发布用例依赖最小的配置读取/发布契约；Nacos 和 Consul 适配器各自翻译键、权限、版本及错误，不把厂商 SDK 类型暴露给页面或 Sentinel Engine。应用读取端继续使用自己的 RuleSource Port。`SentinelRuleCodec` 在管理服务边界将 §4.3 的同类 JSON array 映射到/映射自完整 canonical `RuleSnapshot`；规则发布以完整快照为单位，单条表单编辑也须生成、验证并发布完整候选快照；不能直接改某个进程的内存规则。

设计模式候选是 **Adapter**：Nacos Admin API 和 Consul KV 的键、条件写与错误语义不同，需由各自适配器映射到管理服务拥有的最小发布契约。这不是仅换一个 URL 的薄包装；收益是页面/发布用例不依赖具体 SDK，代价是不能抹平 Nacos 与 Consul 的原生并发保证。发布、校验、回读和生效跟踪仍由普通用例编排，不因有多个步骤就额外发明通用工作流框架。编码前要对两实现运行同一份成功、冲突、离线、权限、回读不一致和关闭资源契约测试；厂商特有能力另外测试。模式选择属于后续代码详细设计评审，本草案不构成代码实施签字。

Nacos 3 使用 `namespaceId + groupName + dataId`，控制台写入走配置管理 Admin API；Consul 使用 KV key，写入使用 `ModifyIndex` 条件更新。控制台自己的规则版本 `(epoch, revision, checksum)` 与配置中心原生版本/索引是两层身份，不能跨厂商按字符串比较。Nacos 3 Admin 发布文档未列出等价的条件写参数，因此发布前重读并比较基线，发现外部修改即阻断、要求用户重新合并；同时尽量将常规写权限收敛到管理服务。此措施**不提供**与 Consul CAS 等价的跨外部写者原子保证，产品不得作此承诺。

发布状态必须分别展示「已验证」「配置中心写入成功」「回读一致」「N 个实例已加载、M 个未知/落后」「完成/部分生效/失败」。实例真正生效需要可信的应用版本回执及在线实例口径，不能仅凭配置中心返回成功或监听器存在推断。回滚是把旧快照作为一个新版本发布。历史记录、草稿和审计的可靠性按所选后端和管理侧存储能力说明；不能把 Consul KV 伪装成与 Nacos 历史/灰度完全对等。

### 5.1 版本、定时生效与自动回退

草稿解决“尚未发布的修改”，版本解决“可追溯、可再次发布的完整规则集”，定时计划解决“在指定时期使用指定版本”。三者不可混为同一个可变对象：

1. 草稿可编辑，但不能直接成为计划目标。
2. 通过校验的草稿固化为一个**不可变完整 `RuleSnapshot` 版本**；版本记录至少含 `version_id`、`base_version_id`、checksum、创建人/时间、发布说明、目标配置绑定与 schema profile。
3. 生效计划只引用版本：`activate_at`、可选 `deactivate_at`、必填 `restore_version_id`、IANA 时区和计划状态。高峰期结束时发布 `restore_version_id` 指向的日常版本，不能采用“恢复到当时系统碰巧处于的版本”这种不确定语义。
4. 一条规则集绑定在同一时刻只允许一个 active 或 scheduled activation plan；重叠窗口、跨时区歧义窗口和已被手工覆盖的基线必须拒绝创建，而不是按 UI 列表顺序猜测。

以“国庆大促保护方案”为例：先从日常版本建立草稿并修改所有必要规则 → 校验后固化为 `promo-version` → 创建 `2026-09-30T19:00:00+08:00` 至 `2026-09-30T23:30:00+08:00` 的计划，`restore_version_id` 明确为日常版本 → 开始时完整写入 `promo-version`，结束时完整写入日常版本。两次写入都要回读并等待实例版本回执；“计划已触发”不等于“所有实例已生效”。

调度器属于独立管理服务，不属于浏览器、RuleSource 或业务应用进程。它必须持久化计划和执行状态、基于 `(plan_id, action, target_version_id)` 做幂等执行、服务重启后恢复未完成任务，并在每次写入前重新读取配置中心的基准版本。若发现计划外的外部修改，计划进入 `blocked_by_conflict`，不覆盖新配置；需要运维人员基于当前版本重新合并或明确取消计划。Nacos 的发布没有等价 Consul CAS 的原子条件写时，仍遵守 §5 的重读/比较/阻断策略，不能承诺绝对的外部并发排他性。

线上规则内容仍只存在 Nacos/Consul；管理服务可以使用可靠数据库保存**版本元数据、草稿、计划、执行记录和审计**，但该数据库不是运行时 RuleSnapshot 的直接规则源，也不能让应用从它加载规则。当前 1.0 中 Cluster Token Server 的额度修改需重启才能生效，因此版本页必须单独标记“配置已切换，目标实例待重启”，不能把计划完成显示为热更新完成。

同一应用/环境/规则集同一时间只能有一个写入目标。Nacos↔Consul 迁移是单独的复制、校验、切换和回退流程，不默认双写。配置源不可达、配置冲突、规则校验失败或实例生效回执缺失分别提示；默认不把「保存成功」说成「热更新完成」。Cluster Token Server 配额在当前 1.0 仍需按新配置重启，相关规则显示「已保存，待重启生效」。

## 6. 分阶段落地与验收

1. **契约先行**：冻结配置键映射、完整快照发布状态、最小权限、指标口径与实例生效回执；修订原有「库内 Dashboard 不跨进程」和「独立控制台可管理规则」的边界。独立管理服务不纳入 M6.6 per-process 交付勾选。
2. **单实例观测增强**：先让 embedded 页面准确显示本进程曲线和采样质量；补计数器/RT 分布与可选进程采样，保持主包零第三方依赖。未接入的主机/TPS 指标明确不可用。
3. **独立控制台最小闭环**：Nacos/Consul 双适配器、场景化规则编辑、校验/差异、完整快照写入/回读、两项权限、审计、发布与回滚状态；选定指标后端后做跨实例图表。真实双后端冲突、离线、实例落后与重启场景验收通过，才宣称生产可用。
4. **后续增强**：持久草稿、多人审批、灰度发布、长期历史和告警按明确存储/后端能力独立评审，不预先放进首版。

验收时要分别报告：静态/契约测试、Nacos/Consul 真实写回、实例实际加载、主机/容器/进程指标采集、QPS/TPS/RT 口径核验以及跨实例聚合。任何一个通过都不能替代其他边界。
