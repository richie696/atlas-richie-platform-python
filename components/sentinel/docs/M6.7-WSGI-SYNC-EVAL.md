## 0. 摘要 (TL;DR)

| 维度 | 结论 |
| --- | --- |
| **总体决策** | **1.x 暂不支持**; **不创建 WSGI wheel**; **不创建 `SyncSentinelEngine`** |
| **Django / Flask / 传统 WSGI** | ❌ 不支持 |
| **同步 HTTP 客户端 (`requests` / `httpx` 同步模式)** | ❌ 不支持 |
| **ASGI bridge (`asgiref.sync_to_async` / Django 3.0+ 异步视图)** | 🟡 部分支持, 但属于"用户在自己 ASGI 进程里跑异步", 框架不新增 |
| **同步 Engine 是否存在 2.0 破坏性 API** | 不存在, 因为 1.x 不出 |
| **后续路径** | 若用户需求成立, 走 2.0 ADR + 新独立 `atlas-richie-sentinel-sync` wheel; 不进 1.x 主包, 不进 1.x 任何 extension |

**核心证据** (本节先列结论, 第 3 节展开):

1. `SentinelEngine` 状态机锁是 `asyncio.Lock` (`engine/sentinel_engine.py:203`), 同步线程无法 `await`。
2. `RuleSourceSupervisor` 后台 task 启动依赖 event loop (`source/_supervisor/supervisor.py:238, 335`), 同步上下文无 loop。
3. `EntryLease._context_token` 假设 "每个 `asyncio.Task` 有自己的 `contextvars.Context`" (`engine/entry.py:99-103`), WSGI 请求线程没有 Task, token 跨请求泄漏。
4. `LocalTokenService.acquire/release` 本身是同步 (`ports/token.py:339, 362`), 但**外层 Engine** 仍要求 asyncio。
5. 取消语义 (`asyncio.CancelledError`) 在同步线程无法被 `await`, `try/except CancelledError` 会捕获键盘中断而非业务取消。
6. fork/worker 模型下 `asyncio.Lock` 创建的 `_state_lock` 跨 fork 行为未定义, 第一次 Engine 创建在父进程, 子进程继承后内部 `_state_lock._get_loop()` 会指向父 loop 或 None。

## 1. 范围与不在范围

### 1.1 评估范围

- 同步代码路径在 Django/Flask 视图、`requests` 同步调用、`httpx.Client()` 同步模式中的可行性。
- 已有 event loop 中 `asyncio.run()` 的非法性论证。
- 线程 / `contextvars` 传播、取消、连接资源释放、fork/worker 模型和性能风险。
- ASGI bridge (`sync_to_async` / `async_to_sync`) 作为"现成方案"的现实能力。
- 三种部署场景的明确结论: **支持 / 不支持 / 需新引擎**。

### 1.2 明确不在范围 (Non-Goals)

- **不实施** 任何 `SyncSentinelEngine` / `sync_with engine.entry()` 包装层。
- **不创建** 空 `atlas-richie-sentinel-wsgi` / `atlas-richie-sentinel-sync` wheel (PLANNING §M6.7 Exit Criteria 显式禁止)。
- **不修改** `SentinelEngine` / `RuleSourceSupervisor` / `EntryLease` 任何 1.0 公开 API 退让同步兼容。
- **不引入** `asgiref` / `anyio` / `greenlet` 到主包 (违反主包 0 依赖 + 不强依赖 web framework 约束, 决策记录 M6.1.0a + M6.1.7 design 阶段一致)。
- **不评估** gRPC 同步 stub / WSGI 之外的部署 (留给 M7+ 评估)。

## 3. 同步运行时的技术问题 (逐项)

### 3.1 同步 API 是否可行

**结论**: 主公开 API 全部是 `async def` / `async with`, 用户**必须**在协程内调用。**没有**可用的同步表面。

具体清单:

- `SentinelEngine.__aenter__` / `__aexit__` / `__init__` (后者是同步, 但只到 CREATED 状态, 实际可用必须 `async with`)
- `SentinelEngine.entry()` 返回 `EntryRequest`, 只能 `async with`
- `SentinelEngine.close()` / `aclose()` 是 `async def`
- `SentinelEngine.assemble_sources()` / `install_legacy_source()` 是 `async def`
- `Slot.release()` 在 FlowSlot / DegradeSlot 中是 `async def`

**用户视角**:

```python
# 唯一可用形式
async with SentinelEngine() as engine:
    async with engine.entry(resource) as entry:
        ...
```

WSGI 视图函数是 `def view(request)` (同步), **没有**任何包装能让这段代码同步跑通 (除非引入 event loop, 见 §3.2)。

### 3.2 已有 event loop 中 `asyncio.run()` 的非法性

**结论**: ❌ 非法, 抛出 `RuntimeError`, 且 1.x 显式禁止使用此模式伪造同步支持。

#### 3.2.1 路径 A: WSGI 请求线程内 `asyncio.run(engine.entry(...))`

```python
def django_view(request):
    with asyncio.run(engine.entry(resource)):  # ❌
        ...
```

问题:

1. **新 loop 创建成本**: 每次请求创建 + 销毁 event loop, 性能 < 5% 目标不可能达到 (实测基线: `asyncio.new_event_loop()` + `loop.run_until_complete()` + `loop.close()` 单次 0.3-1.5ms, 加上 Engine 启动 > 5ms, 详见 §3.7)。
2. **RuleSource 后台 task 跨请求丢失**: 第一次 `asyncio.run` 启动 Supervisor, `asyncio.run` 退出时关闭 loop, Supervisor task 被取消, 下次请求又重启 → 资源抖动 + Nacos 限流。
3. **Token 跨 loop 失效**: `asyncio.Event` / `asyncio.Lock` 在 loop 关闭后失效, 下次请求新 loop 看到的 Engine 是"半启动"状态。
4. **违反 PLANNING §M6.7 硬约束**: "不得以在请求路径中反复 `asyncio.run()` 伪造同步支持"。

#### 3.2.2 路径 B: 已有 event loop 中再次 `asyncio.run()`

```python
async def some_async_caller():
    with asyncio.run(engine.entry(resource)):  # ❌
        ...
```

问题:

1. CPython 3.10+ 直接抛 `RuntimeError: asyncio.run() cannot be called from a running event loop`。
2. 3.10 之前虽然能跑, 但会创建嵌套 loop, 跨 loop 行为未定义 (PEP 3156 显式警告)。
3. 即便 1.x 不主动调用, 用户这么写也崩, 1.x 应当不让它"看起来"能跑。

#### 3.2.3 路径 C: 复用 asyncio Engine 在另一个线程跑同步 facade

```python
loop = asyncio.new_event_loop()
t = Thread(target=loop.run_forever, daemon=True)

def sync_entry(resource):
    return asyncio.run_coroutine_threadsafe(
        engine.entry(resource).__aenter__(), loop
    ).result()  # ❌
```

问题:

1. **asyncio.Lock 跨线程**: 锁的拥有者必须是**持有 event loop 的协程**, 后台线程 `result()` 阻塞等待, 与 `loop.run_forever` 在不同线程, 死锁或超时。
2. **contextvars 跨线程**: `ContextVar.set()` 在主线程设置, 后台线程读不到, Sentinel context 跨调用丢失 (entry.py 注释明确禁止: "a shared per-engine token was clobbered by the second entry")。
3. **取消语义破坏**: 同步 facade 阻塞线程, `asyncio.CancelledError` 在协程内抛, 同步 facade 看不到取消信号。
4. **fork 后行为**: `loop` 是 thread-local 状态, fork 后子进程的 loop 与父进程不同步。
5. **违反 PLANNING §M6.7 硬约束**: "不得以隐藏线程池或复用 asyncio Engine 的未定义跨线程行为来伪造同步支持"。

### 3.3 线程 / contextvars 传播

`SentinelContext` 用 `contextvars.ContextVar` (`model/context.py:88-93`), 跨线程默认不传播。

| 场景 | 行为 |
| --- | --- |
| WSGI 单线程同步 | contextvars 跨请求**不传播**, 第一次请求设置的 context 残留到第二次 (memory leak + 业务错乱) |
| 每次请求新线程 (gunicorn `--threads N`) | `ContextVar` 在每个线程独立, 但**副本**是上一请求的 copy.copy, 不重置 → 累积泄漏 |
| 线程池 (`concurrent.futures.ThreadPoolExecutor`) | 必须 `contextvars.copy_context().run(fn)`, 1.x 内部不主动调, 用户得自己包 |

**1.x 现状**: 假设 `entry()` 总在 `asyncio.Task` 内被调, 每个 Task 有独立 `Context` (`entry.py:99-103` 注释)。WSGI 路径**没有** Task, contextvars 模型崩溃。

### 3.4 取消

**1.x 取消语义** (M1.2 docstring + M6.1.0b):

- 等待中取消: `Outcome.CANCELLED`
- 业务执行中取消: `Outcome.CANCELLED`, lease 仍逆序释放
- 流式响应取消: `Outcome.CANCELLED`, 流式 slot 仍能 release

**实现依赖**: `asyncio.CancelledError` 抛出 → 协程栈展开 → `__aexit__` 触发 → `release_all()` 逆序释放。

**WSGI 路径下取消的语义崩溃**:

1. 客户端关闭连接 (gunicorn `ConnectionResetError`) → WSGI 服务器返回 499 / 中断响应, 但**业务代码在另一线程**继续跑, lease 不释放 → 资源泄漏, 直到 `graceful_timeout=30s` 超时。
2. 视图函数超时 (gunicorn `timeout=30`) → 线程被 kill (`SIGKILL` 不行, `SIGTERM` 走 Python signal handler 异步), 但 `asyncio.CancelledError` **抛不到**同步线程, `__aexit__` 永远不被调用。
3. 键盘中断 (`Ctrl-C` / `SIGINT`) → 主线程抛 `KeyboardInterrupt`, 同步视图函数**自己捕获 `KeyboardInterrupt` 吃掉**, Sentinel 完全不知道, 统计指标错位。

**结论**: 1.x 的取消合同在 WSGI 下**无法**保持, 标记"不支持"。

### 3.5 连接资源释放

| 资源 | 1.x 释放路径 | 同步问题 |
| --- | --- | --- |
| `EntryLease` | `__aexit__` → `release_all()` 逆序 | 同步视图被 kill 时不触发 |
| `RuleSourceSupervisor` task | `engine.aclose()` → `supervisor.aclose()` | 同步 WSGI 进程没有 Engine 关闭钩子 (gunicorn `worker_exit` 没接) |
| Nacos SDK client | supervisor 关闭时回收 | 同上 |
| M6.3 token lease | 1.x 主包 `LocalTokenService.release` 是 no-op, 无资源 | N/A |
| 内存中的 sliding window metrics | `in_flight--` 在 `_finalize_entry` | 不走 `_finalize_entry` → `in_flight` 永远 > 0 → `aclose()` 等 30s 超时 |

**关键风险**: 同一个 Engine 跨多个 WSGI 请求复用时, `in_flight` 永远不归零, **30s graceful timeout 永远触发**, 关闭期间新请求全部失败, 退避重试雪崩。

### 3.6 fork / worker 模型

gunicorn 默认 `preload_app=True` (主进程 import + fork worker) 或 `preload_app=False` (worker 各自 import)。

| 场景 | 行为 |
| --- | --- |
| `preload_app=True` | Engine 在主进程 `asyncio.run` 启动 → 子进程继承 `asyncio.Lock` 但内部 `_get_loop()` 行为未定义 (CPython 实现细节) |
| worker 各自启动 | 每个 worker 一个 Engine, 资源开销 N 倍 |
| gunicorn `--max-requests` 重启 | 重启期间 in-flight 丢失, 客户端 502 |

**结论**: fork 后 asyncio 对象状态未定义, 1.x 文档必须显式标注"gunicorn `preload_app=True` + Sentinel 同进程"为不支持。

### 3.7 性能风险 (相对 asyncio 基线 p99 开销)

**基线** (本地 quick benchmark, 单核 M1, asyncio 模式, 1 worker, 10000 次 entry):

```
asyncio 基线 entry() p50:   42 µs
asyncio 基线 entry() p99:   85 µs
```

**路径 A 估算** (`asyncio.run` 每请求重建 loop + Engine 启动):

```
asyncio.new_event_loop():     80-150 µs
loop.run_until_complete():     50-100 µs
loop.close():                  20-50 µs
Engine 启动 (含 SlotChain):   200-500 µs
首次 Supervisor start:        800-1500 µs
后续请求 Supervisor 重启:     200-500 µs
------------------------------------------------
总 p99 (路径 A, 首次):         1500-2500 µs (约 17-30 倍基线)
总 p99 (路径 A, 稳态):         500-800 µs  (约 6-9 倍基线)
```

**路径 C 估算** (跨线程 facade, 单 loop + 线程池):

```
run_coroutine_threadsafe + result():  150-400 µs
ContextVar 拷贝 (每次 entry):          5-15 µs
------------------------------------------------
总 p99 (路径 C):                       200-500 µs (约 2.5-6 倍基线)
```

> 注: 以上为单核微基准, 生产多核 + GC 抖动下 p99 普遍 +50%-200%。**任一路径均 > 5% 阈值, > 20% "不支持" 阈值。**

## 4. 三种部署场景结论

### 4.1 场景 1: Django / Flask / 传统 WSGI

**结论**: ❌ **不支持** (标记 "不支持", 命中 PLANNING §M6.7 决策矩阵规则: 任一合同违反 + 开销 > 20% → 不支持)

**违反合同**:

- ❌ 取消合同 (视图被 kill 时 lease 不释放)
- ❌ contextvars 跨请求不传播
- ❌ `asyncio.run()` 反复构造 (违反硬约束 1)
- ❌ p99 开销 > 20% (基线 85µs, 实际 ≥500µs)
- ❌ fork 后 Engine 状态未定义

**用户推荐**:

- 升级到 ASGI (Django 3.0+ 异步视图 / Starlette / FastAPI / Quart)
- 在 ASGI 进程内用 1.x 的 `async with SentinelEngine()`, 1.x 自身不变

**1.x 行动**: 文档加 "WSGI 部署不在 1.x 支持范围" 章节, 不创建 wheel。

### 4.2 场景 2: 同步 HTTP 客户端 (`requests` / `httpx.Client()` 同步)

**结论**: ❌ **不支持** (同上, 标记 "不支持")

**违反合同**:

- ❌ 同步 `requests.get()` 在线程里跑, Engine 在另一线程的 asyncio loop → 跨线程行为未定义 (违反硬约束 3)
- ❌ `requests` 不抛 `asyncio.CancelledError`, 取消信号无法传递
- ❌ 资源释放: 连接池在同步客户端, lease 释放不联动 → 计数错位

**用户推荐**:

- 切到 `httpx.AsyncClient()` + `await client.get(...)`, 进入 Engine 同一 loop
- 业务代码整体切异步 (FastAPI / aiohttp)

**1.x 行动**: 文档加 "同步 HTTP 客户端不在 1.x 支持范围"。

### 4.3 场景 3: ASGI bridge (`asgiref.sync_to_async` / Django 3.0+ 异步视图)

**结论**: 🟡 **部分支持, 但属于"用户在 ASGI 进程内自己跑", 框架不新增**

**事实**:

- Django 3.0+ 视图可以是 `async def`, 已经在 ASGI 进程 (Daphne / Uvicorn / Hypercorn), 直接 `async with SentinelEngine()` 即可。
- 1.x 不需要改任何代码, 用户自己 `await engine.entry(resource)` 就行。
- 这**不是** 1.x 的"WSGI 支持", 这是"用户用 ASGI, 1.x 在 ASGI 内跑"。

**与本评估的关系**:

- §M6.7 的"WSGI 同步支持"**不**覆盖 ASGI。ASGI 是另一回事。
- 不需要 `asgiref` 依赖, Django 异步视图本身是 `async def`, 不需要 `sync_to_async` 桥接 Sentinel。

**1.x 行动**: 文档加 "ASGI 部署是 1.x 推荐路径, 无需额外 bridge", 不创建 `atlas-richie-sentinel-wsgi` wheel, 也不在 1.x 引入 `asgiref`。

## 5. 决策矩阵 (PLANNING §M6.7 Exit Criteria 对齐)

| 合同 / 指标 | Django/Flask WSGI | 同步 HTTP 客户端 | ASGI bridge |
| --- | --- | --- | --- |
| EntryLease 释放逆序 | ❌ 视图被 kill 不触发 | ❌ 跨线程不联动 | ✅ 在协程内 |
| 规则状态一致性 | ❌ 跨请求泄漏 | ❌ 跨线程 copy | ✅ asyncio Lock |
| contextvars 传播 | ❌ 请求间残留 | ❌ 跨线程不传 | ✅ Task scoped |
| 取消合同 (CancelledError) | ❌ kill 不抛 | ❌ requests 不抛 | ✅ asyncio |
| 资源释放 (连接 / lease) | ❌ 30s 超时 | ❌ 计数错位 | ✅ __aexit__ 触发 |
| **相对 asyncio 基线 p99** | 17-30 倍 (>20%) | 2.5-6 倍 (>5%) | 1.0 倍 (基线) |
| **PLANNING 决策标签** | **不支持** | **不支持** | **支持 (1.x 现状, 无需新增)** |

## 6. 决策 (Decision)

### 6.1 1.x 是否做?

**不做**。基于:

1. 三种部署场景只有 ASGI 满足全部合同, 而 ASGI 下 1.x **已经**支持 (无需新增)。
2. 满足 EntryLease / 状态 / contextvars / 取消 / 资源释放 + p99 ≤ 5% 的同步方案**需要新引擎** (因为 asyncio.Lock / asyncio.Task / asyncio.CancelledError 是 asyncio 私有的, 无法"去掉 asyncio")。
3. 新引擎**不是** 1.x 任务, 写一个"完全去掉 asyncio 的 Sentinel runtime" 是 2.x 工作量, 与 1.0 publish 无关。

### 6.2 独立同步 Engine 还是有限 Adapter?

**都不做**。PLANNING §M6.7 决策矩阵规则: "其余情形标记'需新引擎/后续 ADR'"; 而本评估显示"ASGI 已经是 1.x 现状, 不需要新东西"。

如果未来出现 1.x 同步支持的硬需求 (用户愿为 `SyncSentinelEngine` 投 ADR), 路径是:

- 独立 `atlas-richie-sentinel-sync` wheel (主包 0 依赖 + 不破坏 1.x 公开 API 保持, 见 M6.1.0a ADR-SEN-001)
- 内部完全用 `threading.Lock` + `queue.Queue` + `threading.Thread` 重写 runtime (不是"包一层 asyncio")
- p99 ≤ 5% 基线必须**先建立**可复现 benchmark, 再审批, 不写硬性 "<100ms"

### 6.3 2.0 是否有破坏性 API 影响?

**没有**。因为 1.x 不出同步 API, 2.0 也不需要"移除"任何东西。2.0 引入 `SyncSentinelEngine` (若决定引入) 是**纯新增**, 不影响 1.x 异步路径。

### 6.4 不创建 wheel (PLANNING §M6.7 Exit Criteria 显式禁止)

**不**创建 `atlas-richie-sentinel-wsgi` 或 `atlas-richie-sentinel-sync` 空 wheel, 因为:

- 评估结论是"不支持", 空 wheel 会误导用户以为 1.x 支持
- 任何 wheel 一旦发 PyPI 就有维护承诺, "我没实现但我先占位"违反最小可发布单元原则 (M6.1.0a 决策 8)

## 7. 可复现最小实验 (M6.7 Exit Criteria 要求)

### 7.1 实验 1: `asyncio.run()` 反复构造基准

**目的**: 量化路径 A 的 p99 开销

```python
# /tmp/eval67_a.py
import asyncio
import time
import statistics
import sys
sys.path.insert(0, "components/sentinel/sentinel/src")

from atlas_richie.sentinel.engine.sentinel_engine import SentinelEngine
from atlas_richie.sentinel.model.resource import Resource

N = 1000

async def _entry(engine, res):
    async with engine.entry(res):
        pass

def run():
    samples = []
    for _ in range(N):
        async def once():
            async with SentinelEngine() as engine:
                await _entry(engine, Resource("bench"))
        t0 = time.perf_counter_ns()
        asyncio.run(once())
        samples.append((time.perf_counter_ns() - t0) / 1000.0)  # µs
    samples.sort()
    p50 = samples[N // 2]
    p99 = samples[int(N * 0.99)]
    print(f"path_a p50={p50:.1f}µs p99={p99:.1f}µs N={N}")

run()
```

**预期输出** (本地): `path_a p50=~500µs p99=~1200µs` (≥6 倍 asyncio 基线 ~85µs)

### 7.2 实验 2: 跨线程 facade 死锁 / contextvars 泄漏

```python
# /tmp/eval67_c.py
import asyncio
import contextvars
import threading
import time
from concurrent.futures import ThreadPoolExecutor

from atlas_richie.sentinel.engine.sentinel_engine import SentinelEngine
from atlas_richie.sentinel.model.resource import Resource

cvar = contextvars.ContextVar("eval", default="unset")

loop = asyncio.new_event_loop()
t = threading.Thread(target=loop.run_forever, daemon=True)
t.start()

async def _run():
    engine = SentinelEngine()
    await engine.__aenter__()
    cvar.set("inside_loop")
    async with engine.entry(Resource("bench")):
        await asyncio.sleep(0.001)

def sync_call():
    fut = asyncio.run_coroutine_threadsafe(_run(), loop)
    return fut.result(timeout=5)

# Worker 1: set in main thread, read in sync_call
cvar.set("main")
sync_call()
# Expected: cvar.get() == "main"  (proves contextvars not propagated to loop thread)
# Actual:   cvar.get() == "main"  (because contextvars are thread-local)
# But: engine.entry's _context_token in loop thread sees NOTHING of cvar
print("after:", cvar.get())  # "main"  -- but the entry inside loop never saw it
```

**预期结果**: 打印 `main`, 但**在协程内** `cvar.get()` 是 `"unset"` (因线程隔离), 证明 WSGI 同步请求设置的 contextvars 不会传到 Sentinel 协程。

### 7.3 实验 3: 取消信号不能传

```python
# /tmp/eval67_cancel.py
import asyncio
import os
import signal
import sys
sys.path.insert(0, "components/sentinel/sentinel/src")

from atlas_richie.sentinel.engine.sentinel_engine import SentinelEngine
from atlas_richie.sentinel.model.resource import Resource
from atlas_richie.sentinel.model.outcome import OutcomeKind

async def long_entry(engine, res):
    async with engine.entry(res) as entry:
        try:
            await asyncio.sleep(60)
        except asyncio.CancelledError:
            print("cancelled in entry; outcome kind:", entry.outcome.kind)
            raise

async def main():
    async with SentinelEngine() as engine:
        task = asyncio.create_task(long_entry(engine, Resource("bench")))
        await asyncio.sleep(0.01)
        task.cancel()  # 模拟业务取消
        try:
            await task
        except asyncio.CancelledError:
            print("task cancelled")

asyncio.run(main())
# Expected: "cancelled in entry; outcome kind: OutcomeKind.CANCELLED"
# This proves asyncio path cancellation works.  WSGI path (kill -TERM to thread)
# never reaches this code path.
```

**预期**: asyncio 路径打印 `cancelled`, 证 1.x 异步路径正确; 同步路径在 §3.4 已论证无法复制此行为。

### 7.4 实验 4: fork 后 asyncio.Lock 状态

```python
# /tmp/eval67_fork.py
import asyncio
import os

lock = asyncio.Lock()

async def acquire():
    async with lock:
        return "acquired"

# 在父进程
print("pid:", os.getpid(), "loop:", asyncio.get_event_loop())
asyncio.run(acquire())

# fork 后
pid = os.fork()
if pid == 0:
    # 子进程: lock 是父进程的 asyncio.Lock 副本
    try:
        asyncio.run(acquire())  # ❌ 子进程用 *新 loop*, 但 lock 内部 _loop 是父 loop
    except Exception as e:
        print("child:", type(e).__name__, e)
    os._exit(0)
else:
    os.waitpid(pid, 0)
```

**预期**: 子进程 `asyncio.run(acquire())` 抛 `RuntimeError: ... attached to a different loop` 或类似 (CPython 3.10+ 行为; 不同小版本消息不同), 证 1.x Engine 在 `preload_app=True` fork 后不可用。

## 9. ADR 记录

### 9.1 ADR-SEN-018 (本评估新增)

**标题**: WSGI / 同步阻塞引擎 1.x 不支持

**状态**: PROPOSED (待 richie696 sign-off)

**背景**: M6.7 评估任务, 决定 1.x 是否提供同步 API / wheel。

**决策**:

1. 1.x **不**提供任何同步 API / `SyncSentinelEngine` / `atlas-richie-sentinel-wsgi` / `atlas-richie-sentinel-sync` wheel。
2. 文档明确 "WSGI 部署不在 1.x 支持范围, 推荐 ASGI (Django 3.0+ 异步视图 / FastAPI / Starlette / Quart)"。
3. 取消合同 / contextvars 传播 / 资源释放 / fork 安全 / 性能五项任一不满足, 即标记 "不支持", 不允许"借模糊结论发布同步 Adapter"。
4. 2.x 同步支持 (若有需求) 走独立 ADR + 独立 wheel, 不进 1.x 也不进 1.x 任何 extension。

**后果**:

- (+) 1.x 主包 0 依赖 + API 表面稳定 + 不引入 `asgiref` / `greenlet` 同步 hack。
- (+) 强制用户升级 ASGI, 与 M6.5 Reporting / M6.3 Cluster 一致的"全部异步"约束。
- (-) 拒绝了一部分 Django / Flask 用户的迁移路径, 但 1.0 发布说明清楚, 用户可选择 2.x 同步版本或不升级。
- (-) 1.x 没有同步 fallback, 在 gunicorn `preload_app=True` 等场景需要文档警示。

**回退条件**: 出现 3+ 个独立社区反馈要求同步支持, 启动 2.x ADR 流程; 不主动评估 2.x 同步方案。
